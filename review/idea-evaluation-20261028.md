> 결론: 흐름(노출 → DB화 → 요청 → 답변지 → 연결 → 협상)은 일관되게 설계되어 있고 한계 공개도 정직하다. 그러나 (1) 사내에서 이 문제가 실제로 있는지, 기존 도구와 무엇이 다른지 조사한 근거가 없고, (2) 무상·교환만 다루는 "거래"에서 에이전트가 협상할 내용이 거의 없어 AI 필요성이 약하며, (3) "p2p라서 중앙 병목이 없다"는 핵심 차별 주장은 로컬 프로세스 시연으로 증명되지 않고 broker 의존과 자기모순이다. 이 셋이 Q&A에서 가장 크게 감점될 지점이다.

## 1. 치명적 결함

치명 등급은 없음. 단 아래 높음 등급 중 R3-1(p2p 주장), R1-3(거래의 실체), R2-1(p2p 허용 여부)은 같은 뿌리를 공유한다. "무엇이 p2p이고 왜 그것이 가치인가"가 답해지지 않으면 이 아이디어는 "사내 검색 + 일정 조율 봇"으로 환원된다.

## 2. 항목별 지적

### R1 핵심 전제·문제 정의

**R1-1 [높음][사업] 문제의 실재성이 검증되지 않았고, 사용 사례가 이질적이다.**
- 근거: hackathon-proposal 문항 1, 문항 4(`[가정]`), proposal-notes 미해결 과제 첫 항목("조사 없이 쓴 것").
- 세미나 좌석, 유휴 장비, 노하우는 사용자·빈도·현재 해법(사내 게시판, 자산관리, 메신저, 위키)이 전부 다르다. 어느 하나라도 "지금 사람들이 이렇게 불편해한다"는 근거(인터뷰, 문의 건수)가 없다. 문항 1의 "알릴 경로가 없다"는 단정도 과장이다(공지, 사내 장터가 있는 회사가 많다. 이 회사의 실태는 미확인).
- 해결: 사례 하나(예: 세미나 잔여석 또는 장비 대여)를 골라 동료 3~5명에게 현재 방식과 불편을 물어 문항 1·4에 한두 줄 근거로 넣는다. 사례를 줄이면 데모도 선명해진다.

**R1-2 [높음][사업] 공급자의 참여 유인이 비어 있고 콜드 스타트는 시드로 덮었다.**
- 근거: 문항 7 ②③, a2a-transaction 4절("해결되지 않은 과제"), broker-and-discovery 5절.
- 공급자는 노출을 작성·유지하고 에이전트를 운영해야 하는데 돌아오는 것이 없다. 한계는 인정했지만 "그래도 쓰이는 이유"가 없다.
- 해결: 공급자의 이득을 한 문장으로 정한다(예: 세미나 운영 부서는 빈 좌석이 줄어 KPI가 오른다, 총무는 장비 문의 응대가 줄어든다). 노출을 자동 생성(기존 공지에서 에이전트가 추출)하면 공급자 부담이 줄어 AI의 몫도 커진다.

**R1-3 [높음][기술] "거래·협상"에 협상할 내용이 거의 없다.**
- 근거: 문항 2-2, 문항 3-5, a2a-transaction 2~4절, 시연 시나리오.
- 거래 대가가 무상·교환뿐이면 협의 대상은 날짜·시간·수량이다. 이는 캘린더·예약 API와 규칙으로 처리 가능하며 LLM 협상이 필요한 이유가 설명되지 않는다. "최대 3회 협의, 공급자가 수정 제안"은 시나리오를 위해 만든 오가기로 보일 수 있다.
- 해결: 협상이 진짜 필요한 변수를 시나리오에 넣는다(둘 다 부분 충족 가능한 조건, 서로의 노출 맞교환 같은 다변수 조정). 또는 "협상"보다 "조건 확인과 예약 확정"으로 주장을 낮추고 AI의 몫을 broker의 해석에 둔다.

**R1-4 [중간][사업] 기대효과에 기준선과 목표가 없다.**
- 근거: 문항 4. 지표 정의(연결 성공률, 발견 시간)는 정직하지만 현재 소요 시간 같은 기준선이 없고 "해커톤에서 측정"은 시드 데이터로는 의미가 없다(측정 값이 곧 설계 값).
- 해결: 현재 방식의 소요를 소규모로 실측하거나, 측정 불가하다고 명시하고 파일럿 설계를 제시한다.

### R2 보안·법률·사내 규정

**R2-1 [높음][보안] 사내망 p2p 직접 연결의 허용·가능 여부가 미확인이며, 후퇴하면 핵심 주장이 무너진다.**
- 근거: trust-and-security 3절 "p2p 연결"(미확인, 후퇴 시 원칙 약해짐), proposal-notes 가정 3, 문항 6.
- 임직원 PC는 인바운드 연결을 막는 경우가 대부분이다. 에이전트가 어디서 도는지(개인 PC, 서버)도 정의가 없다. 후퇴안(broker 중계)은 곧 중앙 장터이며, 문항 7-1·문항 4 "중앙 병목 회피"가 사라진다.
- 해결: 제출 전에 보안 부서에 확인하거나, 처음부터 "에이전트는 사내 서버에서 호스팅, 직접 연결은 에이전트 간 직접 호출"로 정의해 후퇴 시 주장을 유지할 수 있게 쓴다.

**R2-2 [높음][보안] 책임 소재와 권한: 에이전트가 사람 대신 자원을 확정하는데 책임 주체가 없다.**
- 근거: 문항 4 마지막("broker가 책임을 지지 않습니다"), 문항 7-1, trust-and-security 3절 감사 기록, a2a-transaction 5절(이행 강제 수단 없음).
- "책임이 쌓이지 않는다"를 장점으로 쓰면 보안 담당은 "그럼 사고 시 누가 지는가"를 묻는다. 에이전트가 대신 한 예약·약속의 효력, 오판 시 취소 경로, 감사 로그 보관 주체가 없다.
- 해결: 책임은 소유자에게 있고, 확정 건은 취소 가능하며 최소 로그를 남긴다고 쓴다. "책임이 쌓이지 않는다"는 표현은 삭제한다.

**R2-3 [중간][보안] broker는 전사 노출과 요청이 모이는 집약 지점이며, 공개 범위 제어가 범위 밖이다.**
- 근거: trust-and-security 3절(MVP는 전사 공개만), 문항 3 범위 밖.
- 요청 문장 자체가 민감할 수 있다(예: 특정 프로젝트, 인력 수요). 부서 한정 정보가 전사에 노출되는 것이 기본 동작이다. "요약만 올린다"도 요약이 민감하면 의미가 없고, 검사는 간단한 패턴 수준이다.
- 해결: 데모 도메인을 공개 정보(세미나, 공용 장비)로 한정하고, 이를 문항에 명시한다. 요청 로그 접근 권한을 broker 운영자 기준으로 설명한다.

**R2-4 [중간][보안] "사내 보안을 전제로 한 설계"라는 표현이 구현 범위보다 앞선다.**
- 근거: 문항 7-2 vs trust-and-security 1절(MVP는 사전 발급 키, SSO 없음), 3절(공개 범위 전사만), 프롬프트 주입은 "완전한 방어 불가".
- 신청서 문항 7-2는 구현된 것처럼 읽힌다. 실제로는 서명 키 사전 발급, 허용 LLM `[가정]`뿐이다.
- 해결: "전제로 한 설계" 대신 "다음을 MVP에서 구현/설명만 한다"로 구분해 쓴다.

### R3 기술적 주장의 오류와 자기모순

**R3-1 [높음][기술] "발견은 broker, 거래는 peer"가 중앙 의존을 줄인다는 주장이 과장이며, 시연으로 입증되지 않는다.**
- 근거: 문항 1 마지막, 문항 4 마지막 항목, 문항 7-1, system-overview 4절 3항("단일 장애점이 되지 않는다"), trust-and-security 2절("broker 운영자를 믿어야 한다").
- 발견·순위·일치 근거를 broker가 정하므로 사실상의 게이트키퍼다. 거래 내용만 직접이라는 분리는 의미가 있지만 "중앙 병목 회피", "단일 장애점이 되지 않는다"는 과하다. 사내망에서는 중앙 서버 하나로도 문제가 없는데 왜 p2p인지에 대한 가치 설명이 없다(거래 내용의 비노출 정도가 전부). 시연의 broker 2개는 한 PC의 프로세스라 장애 분산을 보여 주지 않는다.
- 해결: p2p의 가치를 정확히 한정한다("거래 내용과 원본 정보가 broker에 저장되지 않는다"). "병목·단일 장애점 해소"는 삭제하거나 한 broker를 끄고 다른 broker로 동작하는 장면으로 직접 보여 준다.

**R3-2 [중간][기술] a2a 사양이 미확인으로 남아 있고, "p2p"와 A2A의 관계가 정의되지 않았다.**
- 근거: a2a-transaction 1절("미확인"), proposal-notes 미해결 과제. 신청서 본문은 a2a가 무엇인지(표준 프로토콜인지 자체 메시지인지) 밝히지 않는다.
- 확인한 사실: A2A는 2026-03에 v1.0이 릴리스되었고 Linux Foundation 산하이며, Agent Card는 `/.well-known/agent-card.json`에 두고 JSON-RPC, gRPC, HTTP+JSON 바인딩을 정의한다. 클라이언트-서버 호출 모델이라 "p2p 연결"은 NAT 통과 같은 별도 기술이 아니라 에이전트 간 직접 호출이다. 오래된 자료에는 0.3.x가 현행으로 적혀 있다(출처 참조).
- 해결: "A2A v1.0의 Agent Card와 Task 모델을 쓴다(또는 호환 서브셋)"를 문항 3에 명시하고, 구현 전에 공식 문서를 확인한다.

**R3-3 [중간][기술] 문서 간 불일치와 검증 불가 출력.**
- 홉 제한: 문항 3은 "홉 1", broker-and-discovery 3절은 "홉 1~2".
- broker-and-discovery 1절은 "자기 domain이 아니면 맞는 broker로 넘긴다"고 쓰나 홉·순환 규칙과 연결되어 있지 않다.
- "일치 근거 한 줄"은 LLM이 생성하므로 환각 가능성이 있고, trust-and-security 2절이 broker 편향 대응으로 이것을 내세우지만 근거 자체는 검증되지 않는다.
- 해결: 홉을 1로 통일한다. 일치 근거는 원문 필드 인용을 기반으로 하도록 설계하고 그렇게 쓴다.

### R4 독창성

**R4-1 [높음][사업] 차별점이 조사 없이 쓰였고 비교 대상이 허수아비에 가깝다.**
- 근거: system-overview 5절(말미에 "조사를 하지 않았다"), proposal-notes. 비교표의 "중앙 마켓플레이스: 모든 거래를 중개하고 보관한다"는 사내 장터 등의 실제 기능을 확인하지 않은 일반화다.
- 단일 에이전트 + RAG와의 비교("한 에이전트 지식 안에서만")도, 사내 지식 검색에 사람 연결·예약 도구를 붙인 에이전트와 어떤 차이가 있는지 답하지 못한다. 외부 유사 서비스(에이전트 레지스트리·마켓플레이스 형태)에 대한 조사는 미확인이다.
- 해결: 사내 도구 2~3개와 외부 에이전트 디스커버리 사례를 직접 확인해 한 줄씩 비교한다. 차별점은 "요청 기반 발견 + 노출 기반 공급 + 직접 협의"의 조합으로 좁힌다.

**R4-2 [중간][기술] 다중 broker(연합)가 필요한 이유가 없다.**
- 근거: 문항 3-3, system-overview 4절. domain 2개를 한 DB의 필드로 나누면 되므로, broker 간 질의가 AI·분산 가치 없이 복잡도만 더한다.
- 해결: 조직별 소유(총무 broker, 교육 broker처럼 운영 주체가 다름)를 이유로 명시하고, 실제로 운영 주체가 다르다는 시나리오를 시연에 넣는다.

### R5 해커톤 적합성

**R5-1 [높음][기술] 시연이 시드·시뮬레이션이라 핵심 흐름이 "하드코딩"으로 보일 위험이 있다.**
- 근거: 문항 2-4, 문항 3 시연 시나리오, 문항 6(시드 10건, 요청 5건).
- 동일 PC의 에이전트 3~5개가 서로 성향만 다른 LLM이고 시드는 직접 쓴 것이다. 심사위원은 "그 시나리오 외 요청도 되는가"를 묻는다. 시나리오 하나에서 두 broker가 각각 답을 내는 구성은 사전 설계의 인상을 준다. 실패 대비 녹화는 있으나(proposal-notes 일정) 그 외 대안이 없다.
- 해결: 현장 심사위원이 즉석에서 요청을 입력하는 장면을 넣는다(시드 범위 내 질문임을 사전 검증). 미스 응답(답변 없음) 장면도 정직하게 보인다.

**R5-2 [중간][기술] 2일 범위가 과다하고 일정에 완충이 없다.**
- 근거: 문항 3의 7개 기능, proposal-notes 일정표. 노출 구조화, 임베딩 검색, broker 간 질의, 협상, 권한 초과, 3패널 대시보드, A2A 호환까지 합치면 2일차 오후에 통합·리허설이 몰린다.
- 해결: 필수(노출→검색→답변지→협상)와 선택(broker 간 질의, 3패널)을 나누고 선택 항목의 포기 기준을 일정에 쓴다.

**R5-3 [중간][사업] 제출본에 `[가정]` 표시가 남아 있고, 제출용과 내부 판단이 섞여 있다.**
- 근거: 문항 3 시연 시나리오, 문항 4 주요 사용자, 문항 6 시스템 행, 문서 상단 안내. 문항 7-3의 "알고 있는 한계"는 솔직하나 4가지를 한 문단에 모두 나열해 첫인상이 방어적이다.
- 해결: 확정 후 마커를 모두 제거한다. 한계는 가장 큰 둘(유인, 진위)만 앞에 두고 나머지는 Q&A 자료로 돌린다.

### R6 권고

**R6-1 [중간][사업] 주장을 좁히고 한 장면에 모을 것.**
- 근거: 전체. 현재는 "정보 장터" 하나에 이벤트·물품·노하우, 발견·p2p·협상이 모두 들어 있다. 가장 강한 가치는 "요청 한 번에 서로 다른 부서의 공급자를 찾아 한 번에 조율"이다. 이 한 문장에 맞춰 문항 1·5·7을 정렬한다.

## 3. 예상 Q&A (현재 문서로 답할 수 있는가)

| # | 질문 | 답 가능 여부 |
|---|---|---|
| 1 | 사내 게시판·메신저·검색과 뭐가 다른가, 이 문제가 실제 있다는 근거는? | 부분적. 차별점은 서술되나 조사·근거가 없음(R1-1, R4-1) |
| 2 | 왜 p2p인가. 사내망에서 중앙 서버 하나면 안 되는가, 허용은 되는가? | 불가. 허용 여부 미확인, 가치 설명 약함(R2-1, R3-1) |
| 3 | 공급자는 왜 노출하고 응하는가? | 불가. 미해결로 인정(R1-2) |
| 4 | 에이전트가 잘못 합의하거나 약속을 어기면 누가 책임지는가? | 부분적. 범위·횟수 상한뿐, 책임·취소 경로 없음(R2-2) |
| 5 | AI 없이 예약 시스템과 검색으로 되지 않는가? | 부분적. broker 해석은 방어 가능, 협상은 방어 약함(R1-3) |

## 4. 잘된 점

- AI가 하는 일과 규칙이 하는 일을 구분해 적었다(broker-and-discovery 4절, 문항 2 서두). AI 장식 비판을 선제 차단한다.
- 한계를 숨기지 않았다(문항 7-3, a2a-transaction 5절, trust-and-security 2절의 "남는 한계" 열). 과장 표현(100%, 완벽 등)은 발견되지 않았다.
- 효과 수치를 지어내지 않고 측정 지표만 제시했다(문항 4).
- 권한 범위와 횟수 상한으로 자율 에이전트의 피해를 제한하고, 범위 초과 시 사람에게 넘기는 장면을 시연에 넣었다(문항 2-2, 3-6).
- 범위 밖 항목을 명시했다(문항 3 말미). 2일 해커톤의 "보여 줄 것과 말로 할 것"의 경계가 대체로 분명하다.
- 시연 실패 대비 녹화가 일정에 있다(proposal-notes).

## 5. 권고 (우선순위)

1. R3-1, R2-1: p2p의 가치를 "거래 내용·원본이 broker에 저장되지 않음"으로 한정하고, 병목·단일 장애점 표현을 삭제하거나 broker 하나를 끄는 장면으로 입증한다. 보안 부서에 p2p 허용 여부를 확인한다.
2. R1-1, R4-1: 사례 하나로 좁히고 동료 3~5명 인터뷰와 사내 기존 도구 2~3개 비교를 문항 1에 반영한다.
3. R1-3, R1-2: 협상에 다변수 조건을 넣거나 주장을 낮추고, 공급자의 이득을 한 문장으로 쓴다.
4. R2-2, R2-4: 책임·취소·감사 로그를 쓰고, "보안 전제 설계" 표현을 구현 범위와 맞춘다.
5. R3-2, R3-3, R5-3: A2A 버전 명시, 홉 통일, `[가정]` 마커 제거.
