# 프로젝트 전제

> 리뷰어가 문서 간 일관성을 검사하는 기준입니다. 전제도 비판 대상입니다.
> `[확정]`은 사용자가 직접 정한 것, `[가정]`은 문서 작성을 위해 임시로 둔 값입니다. `[가정]`은 사용자가 확인하면 `[확정]`으로 바꿉니다.
> 갱신일: 2026-10-28 (현행화: 이전 설계의 전제를 정리하고 현재 결정만 남김. 이전 내용은 git 이력에 있음)

## 1. 무엇을 만드는가

- `[확정]` **이름**: **에이전트 광장 (Agent Agora)**. 사내·아이디어로 범위를 좁히지 않는다. 시연은 그중 하나인 **사내 아이디어 공모**다.
- `[확정]` **핵심 메시지**: 필요하거나 선호하는 정보에 대한 접근과 참여를, 내 AI 에이전트가 **더 능동적으로, 더 제대로, 더 효율적으로** 하게 해 준다. 사내에서 쓸 경우 **정보 접근성 개선**과 **업무 효율 향상**을 강조한다.
- `[확정]` **취지(기존 도구와의 차이)**: peer 에이전트의 적극성과 a2a의 효율이 사람 사이에서 흔한 기회 상실과 비효율을 극복한다. 개인 에이전트가 사내 자원을 혼자 찾아 헤매는 것보다 에이전트끼리 묻는 a2a가 효율적이다.
- `[확정]` **커뮤니티 단위**: 부서·회사·협력사 연합 같은 커뮤니티 단위로 쓸 때 가장 강력하다. 커뮤니티의 경계는 프로필 라벨이고, 게시판·기록은 구성원 peer가 맡으므로 **중앙 서버 자원이나 유지보수 공수가 필요 없다**.
- `[확정]` **역할의 조합이 곧 소통 방식이자 비즈니스 모델**이다(공모, 전문가 상담, 지식·자료 거래, 협업 모집, 인프라 제공). 이번에는 공모만 구현한다.
- `[확정]` **나의 자산**: 구성원(peer와 사람)은 강점·노하우·지식을 계속 쌓을 수 있고, 그것은 자신의 자산이 되며 이 생태계에서 더 잘 드러난다. 자산은 **작업 영역에 쌓인 지식**과 **원장에 드러난 실적**이다. 절대자 peer의 대시보드에 peer별 강점과 실적이 드러난다.

## 2. 구조

- `[확정]` **구성원은 peer 한 종류**다. 역할은 구성원의 종류가 아니라 peer가 맡는 행동이다. 시연의 peer와 역할 배치는 한 예시이며 고정이 아니다.
  - **인프라 역할**(상시 공개, 자발적): broker(게시판·검색), recorder(기록), 추천(recommend). 역할 수행은 기여로 집계되어 보상의 근거가 된다.
  - **이벤트 역할**(건별 역할 계약): 요청자(이벤트 peer), 응모자, 심사자.
- `[확정]` **작업 영역과 자기소개**: 각 peer의 작업 영역에 지식과 경험이 쌓이고, 비서 에이전트가 이를 요약해 정체와 역할을 broker에 게시한다. 경험이 쌓이면 자동 갱신한다. 사람이 편집할 수도 있으나 시연은 자율성을 위해 자동이다.
- `[확정]` **자율형 peer와 a4a**: 여러 유형의 peer 중 특정 권한을 가진 자율형 peer가 있다. 그중 하나는 broker API 권한으로 프로필·공지를 조회·분류·추천한다. a4a(에이전트를 위한 에이전트) 환경에서 사람은 인지조차 못하는 사이 내 peer가 이 peer를 통해 정보를 얻는다. 시연의 추천 peer는 아직 공개 기능만 쓰고 페르소나가 붙어 있다(자율형·권한은 설계).
- `[확정]` **권한은 만기로 관리한다**: broker API 권한, 원장 열람 권한은 회수가 아니라 기간 만료(expire)로 끝난다. 계속 쓰려면 다시 받아야 하고 원장 실적이 갱신의 근거가 된다.
- `[확정]` **broker는 기계적으로 일한다(AI 없음)**: 프로필과 공지(만기 있음)를 게시하고, 공지의 응모 대상 라벨(예: `소속:삼성SDS`)이 맞는 peer 전원에게 그 공지를 보여 준다. 검색은 BM25나 임베딩 같은 검색기가 한다. AI가 필요한 매칭은 **추천 peer**가 broker의 검색기를 써서 자기 AI로 한다.
- `[확정]` **broker 3곳**: 탈중앙화된 모습을 보이기 위해 broker를 3개 쓴다. peer 3~4명이 각 broker에 기본(primary)으로 붙고, 공지는 broker 사이에 공유된다. 프로필은 기본 broker에만 두고 검색은 세 곳에 물어 합친다.
- `[확정]` **응모는 각 peer가 스스로 정한다**: 근거는 ① 작업 노트의 적합성(문장 인용) ② 소유자 규칙 ③ 이득과 여력 ④ 위험 ⑤ 원장으로 확인한 상대 신뢰. 결과는 응모·사람에게 묻기·넘김.
- `[확정]` **아이디어 내용은 사람이 낸다**: 비서는 찾고, 판단하고, 묻고, 제출과 기록을 돕는다. 시연에서는 사람을 대신하는 페르소나 에이전트를 비서와 따로 두었고, 실제 환경에서는 사람이 이 역할을 한다.
- `[확정]` **만남의 순서(시연)**: 심사·기록 역할을 할 peer가 역할을 기간을 정해 공개 → 이벤트 peer가 broker 검색으로 발견해 p2p로 연락 → **역할 계약**(양쪽 서명, 원장) → 공지 게시 → 대상 peer들이 공지를 보고 각자 판단 → 아이디어를 p2p로 제출 → 마감 뒤 계약된 심사자가 심사, 채택.
- `[확정]` 흐름은 코드가 아니라 **AI 에이전트 간 통신**으로 유연하게 흐른다. 코드는 대상 필터, 서명 검증, 원장 규칙, 역할 충돌 규칙만 고정한다.
- `[확정]` **광장 진입과 확장**: peer는 primary broker에 서명한 프로필을 게시하는 순간 광장에 들어오고, 만기가 지나면 내려간다. broker 3곳은 입구가 셋인 하나의 광장이다. broker끼리 연결될수록 광장이 넓어지며(부서 → 회사 → 협력사), 각자 보는 범위는 라벨이 정한다. 연결할 broker는 커뮤니티가 정한다.
- `[확정]` **확장성 예시(구현·시연 대상 아님)**: 채팅 UI 같은 기능은 누구나 앱으로 만들어 broker나 파일 broker(토렌트 방식)로 배포한다. 사람은 회원가입 없이 "채팅방 열고 누구 초대해"라고 말하면 내 peer가 채팅 peer에게 URL을 받아 열고 초대한다. 문항 7에 짧게만 언급한다.
- `[확정]` **문장 기준**: 신청서 문장은 심사위원(대기업 임원)이 듣기 좋은 표현을 고르되 사실과 어긋나지 않게 쓴다. 제출용 압축본은 추후 따로 만든다.
- `[확정]` A2A에는 중앙 서버가 없다. 각 peer가 자기 접속 창구를 열고 서로 직접 호출하며, broker는 주소를 찾게 해 주는 게시판일 뿐 메시지가 거쳐 가지 않는다.

## 3. 원장

- `[확정]` **원장의 목적**: DB나 시계열 로그로 쓰는 것이 아니라 **peer를 평가하거나 peer의 실적을 공증**하기 위한 것이다.
- `[확정]` **분산·탈중앙 설계**: 기록 역할을 맡은 peer들이 각자 보관한다. 시연은 recorder 1명(응모자가 될 수 있는 peer 중 하나, 보안·컴플라이언스 담당)이며, 복수 recorder의 일관성 알고리즘은 공개된 기술이므로 해커톤 이후에 한다. 실제 허가형 블록체인은 확장 경로로만 언급한다.
- `[확정]` 원장 항목에는 참여자 서명과 기록자 서명이 붙는다. 항목 종류는 계약(contract), 먼저 등록(publish), 공유(share), 피드백(feedback: 심사·채택)이다. 내용은 담지 않고 해시·가명·서명(심사 점수 포함)만 담는다.
- `[확정]` recorder는 자신이 기록하는 공모에 응모하지 않는다. 계약 없는 심사와 중복 심사는 원장이 거절한다. 응모자는 기록자 서명 영수증을 보관한다.
- `[확정]` **절대자 peer**: 원장을 마음대로 볼 수 있는 읽기 전용 peer(기록자의 열람 허용 목록에 키가 있음). 대시보드는 이 peer를 통해 원장을 보고 통계와 peer별 강점·실적을 낸다. 내용과 실명은 보지 못한다.

## 4. 신원

- `[확정]` **실명·가명·익명은 커뮤니티의 선택**이다. 회사라면 DID를 인사 프로필과 연결하고, 익명 사회라면 익명으로 한다. 원장과 서명은 어느 방식에서도 같다. 시연 커뮤니티는 회사(삼성SDS 전사원)이며, 화면에는 심사 공정성을 위해 가명으로 표시한다.
- `[합의]` 가명 방식에서 실명 확인은 감사 담당만 하며 사유와 시각을 기록한다(시연은 사유 입력과 기록까지).

## 5. 범위와 제약

- `[확정]` 대회는 대기업 사내 임직원 대상 2일 AI 해커톤이다. 신청서 7개 문항은 주최 측 양식이다. **양식 원문은 `docs/form-original.txt`이며 절대 수정·삭제하지 않는다.** 신청서의 문항 글은 원문을 그대로 옮기고 답변만 쓰며, `review/check_form.py`로 일치를 검사한다(사용자 지시 2026-10-28). **문항 6(선택)은 우리 상황과 무관하므로 답변을 쓰지 않는다.**
- `[확정]` **지금 우선순위는 `docs/hackathon-proposal.md`(제출용 신청서)**다. 구현은 시연 근거를 확인하는 수준으로만 한다.
- `[확정]` **LLM**: 신청서의 계획 LLM은 해커톤에서 제공하는 Claude API다. 삼성SDS클라우드 Simple AI Inference(OpenAI 호환, `gpt-oss-120b`)는 Claude 키가 없는 동안 개발·검증용으로만 임시 사용한다. 키는 저장소 밖(`.env`, git 무시)에만 둔다. 사전 작성 코드 제한 여부는 고려하지 않는다.
- `[확정]` **사내망 보안은 고려하지 않는다**: 망 정책, 사내 허용 서비스, 정보보안·법무 승인은 범위 밖이며 신청서와 리뷰에서 다루지 않는다.
- `[합의]` 보상은 기여 집계와 가시화까지만 한다. 포인트·금전 연계는 범위 밖이다(회사처럼 실명과 연결하는 커뮤니티에서는 실적이 인사 평가의 근거가 될 수 있다).
- `[확정]` **용어**: 생소한 단어 대신 자연스러운 말을 쓴다(역할 계약, 먼저 등록, 기록자 서명, 실명 확인 등). 다이어그램은 Mermaid로 그린다.

## 8. 용어

| 용어 | 정의 |
|---|---|
| peer | 커뮤니티 구성원마다 하나씩 있는 AI 에이전트 단위. 작업 영역, 비서 에이전트, 서명 키(DID)를 가진다 |
| 비서 에이전트 | peer 안에서 공지를 보고 판단하고, 사람에게 묻고, 통신·제출·기록을 하는 LLM 역할 |
| 페르소나 | 시연에서 사람을 대신하는 별도의 LLM 역할. 아이디어를 쓰고, 비서의 질문에 답하고, 심사한다 |
| 작업 영역 | peer의 지식·경험 노트, 소유자 규칙, 현재 상황. 비서가 이를 요약해 자기소개로 게시한다 |
| 프로필(자기소개) | broker에 게시하는 요약, 공개 역할(`offers`), 라벨(`labels`), 버전, 만기 |
| 라벨 | 프로필의 소속 표시(예: `소속:삼성SDS`). 커뮤니티의 경계이자 공지 대상 필터. 시연에서는 스스로 적은 값 |
| broker | 프로필·공지 게시판이자 검색기. AI 없음. peer가 맡는 인프라 역할이며 시연은 3곳 |
| 공지 | 일을 여는 peer가 broker에 게시하는 글. 응모 대상, 조건, 마감, 계약된 기록자·심사자를 담는다 |
| 자율형 peer | 사람 없이 혼자 도는 peer. 일부는 만기가 있는 특정 권한(예: broker API)을 받아 조회·분류·추천을 한다 |
| 추천 peer | 자율형 peer의 한 예. broker 검색기 위에서 자기 AI로 공지와 프로필을 맞춰 보고 근거와 함께 추천한다 |
| a4a | 에이전트를 위한 에이전트. 사람이 아니라 다른 에이전트에게 정보·서비스를 주는 에이전트 환경 |
| 기록자(recorder) | 원장 항목을 검증하고 기록자 서명을 남겨 보관하는 인프라 역할. 시연은 1명 |
| 원장 | peer 평가와 실적 공증을 위한 서명된 해시 체인. 내용은 담지 않는다 |
| 지식 저장소 | 아이디어·심사 의견 같은 내용을 해시 키로 두는 곳. 삭제할 수 있다 |
| 절대자 peer | 기록자의 열람 허용 목록에 키가 있는 읽기 전용 peer. 원장을 검증하고 통계와 peer별 강점·실적을 낸다 |
| 역할 계약(contract) | 이벤트 peer가 다른 peer에게 이벤트 한정 역할(기록자·심사자)을 맡기는 양쪽 서명 원장 항목 |
| 먼저 등록(publish) / 공유(share) / 피드백(feedback) | 보내기 전 등록 / 양쪽 서명으로 넘김 / 심사·채택 |
| 기여(실적) | 낸 아이디어, 받은 사람 수, 채택 수, 심사 수, 맡은 역할, 기록 건수 |
| p2p | broker가 알려 준 주소로 상대 peer를 broker 없이 직접 호출하는 것 |
| a2a | 에이전트끼리 A2A 프로토콜로 요청하고 답하는 것 |
