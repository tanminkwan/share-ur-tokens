## 1. 치명적 결함

치명 등급은 없다. 높음 중 최우선은 다음 셋이다.

1. **R3-14 + R3-13**: 신청서가 근거로 제시한 실행 기록이 신청서 서술과 다르고(네 군데), 원장이 같은 심사자의 같은 아이디어에 대한 중복 심사를 그대로 수락했다. 증거의 정확성 문제라 신뢰도에 직접 닿는다.
2. **R5-8**(3차 낮음 → 이번 중간, 체크리스트 등재): 문항 3이 "이미 구현한 것"의 목록이 되어 해커톤 2일 동안 할 일이 없다. 사전 코드 허용 여부도 미확인이다.
3. **R5-5**(3차, 변동 없음): 아이디어 3건 중 3건 채택, 거름 3명 중 1명은 설정으로 강제된 거름, 심사·작성이 같은 모델. 시연 숫자가 효과를 증명하지 못한다.

### (2) 신청서의 근거 자료(실행 기록)와 신청서 서술의 불일치

**R3-14 [중간][기술] 신청서가 인용한 실행 기록이 신청서의 서술과 네 군데 어긋난다.**
- 근거: 문항 2-1·2-2·3 vs `review/evidence/live-run-gpt-oss-120b.txt`, `app/personas.py` NOTES, `app/nodes.py`.
  1. **"심사를 한 번 중복 요청하는 비효율"(문항 2-1, 7-6⑦)은 중복 요청이 아니다.** 로그 56~57행: 비서의 첫 `request_review`는 `peer_url`이라는 **자리표시자 문자열을 인자로 그대로** 썼고(`→ 가명-:` 빈 가명으로 호출), 그 호출은 실패했다(심사 peer의 "심사 요청 수락" 로그가 없고 두 번째 호출 뒤에만 있다). 즉 "스스로 골라 완료"한 실행의 첫 도구 호출은 **인자를 잘못 채운 실패**였고, 두 번째에 성공했다. 비효율이 아니라 모델이 프롬프트의 예시 문구를 값으로 혼동한 오류다. 사실대로 쓰면 신청서가 더 믿을 만해진다.
  2. **"제출한 peer 4명의 자기소개가 v2로 갱신"(문항 3)은 틀렸다.** 제출한 peer는 3명(3fe48a, bed563, a55521)이고 v2 갱신 4명 중 나머지 1명은 심사자(312ba0)다. system-overview 11절은 "4~5명"으로 또 다르다.
  3. **"약 2분"(문항 3) vs "약 1분"(system-overview 11절).** 로그에 시각이 없어 어느 쪽도 확인할 수 없다.
  4. **문항 2-2의 예시("심사자의 요약에 '작성자를 모른 채 변별력 있게 점수를 준다'는 원칙이 포함됨")는 경험으로 얻은 것이 아니다.** 그 원칙은 `personas.py` NOTES의 p11 **시드 노트**에 처음부터 있고, 로그 23행의 v1 요약에 이미 들어 있다. v2도 같은 문장을 반복한다. "경험이 쌓이자 갱신"의 예시로는 제출자들의 v2(제출한 아이디어 주제가 요약에 들어감, 로그 49~53행)가 맞다.
  5. 작은 것: 문항 3-1 "대시보드의 '피어의 자기소개' 표에서 버전 상승이 보임"은 system-overview 3절 "화면 육안 확인은 ❓"와 충돌한다.
- 해결: 로그를 다시 읽고 문항 2-1·2-2·3의 숫자와 예시를 로그 그대로 고친다. 로그에 시각을 넣어 다시 저장한다(`emit`에 이미 `ts`가 있으니 출력 포맷만 바꾸면 된다). "중복 요청"은 "첫 호출에서 인자를 잘못 채워 실패, 두 번째에 성공"으로 쓴다.

**R3-13 [중간][기술] 원장이 같은 평가자의 같은 아이디어에 대한 중복 심사를 수락해 통계가 두 배가 됐다.**
- 근거: 로그 70행 `심사 완료: 42c3422f=8.0, 42c3422f=8.0, dc1b1929=6.0, dc1b1929=6.0, …`, 61~69행(share 3건 + feedback 6건), 92행 `score_hist {'6': 2, '7': 2, '8': 2}`, `ledger.py` `_check`, `nodes.py` `review`·`request_review`.
- 확인한 것: 심사 페르소나 LLM이 아이디어 3건에 대해 심사 6건(각 2회)을 돌려줬고, `review`는 그대로 서명했으며, `request_review`는 6건 모두 `feedback(review)`로 기록했다. `_check`에는 "같은 평가자가 같은 내용에 review를 두 번 남길 수 없다"는 규칙이 없다. 그 결과 **문항 3의 "원장 19건" 중 3건은 중복**이고, 절대자 통계의 "심사 6건·점수 분포"는 실제의 두 배다. 이번에는 점수가 같았지만 달랐다면 "어느 것이 공식 점수인가"에 원장이 답하지 못한다. 원장이 "분쟁 대비 증거"(문항 4)라면 이 구멍은 바로 질문받는다.
- 해결: `_check`에 feedback(review) 유일성 규칙(evaluator, content_hash, call_id)을 넣고, `review`에서 id별로 한 건만 남긴다. 신청서의 "원장 19건"은 수정 후 다시 실행한 값으로 바꾼다.

### (3) 새 기능(작업 영역·위촉 계약)의 주장과 코드

**R3-15 [중간][기술] "역할은 작업 영역에서 나온다"는 주장과 코드 사이의 간극.**
- 근거: 문항 1·2-2·3-1, system-overview 2절 원칙 2, premises "작업 영역과 자기소개" vs `nodes.py` `advertise`·`learn`·`engage`·`review`, `ledger.py`.
  1. **제공 역할(`offers`)은 작업 영역이 아니라 설정값 `can`**에서 온다. 심사 peer가 심사 원칙을 아무리 쌓아도 `can=["review"]`가 없으면 `engage`·`review`는 코드가 거절한다. 비서가 요약하는 것은 `summary` 문장뿐이다. 신청서 1의 "심사자 peer가 심사에 관한 원칙을 쌓으면 그 원칙이 게시되고 수요자가 연락"은 summary에 한해서만 맞다.
  2. **공개 기간(`until`)은 peer가 정하지 않고 코드가 7일로 고정**한다. 만료는 `find`에만 적용되고 `call`(공모 알림)에는 적용되지 않는다. 문항 2-3 "공개 기간이 지난 역할은 검색되지 않습니다"는 `find`에 한정해 맞고, 시연에서 만료를 보일 방법은 없다.
  3. **"경험"은 코드가 만든 한 문장**이다. `learn`의 입력은 `"사내 공모('…')에 아이디어 '…'를 제출했다"` 같은 템플릿 문자열이고, LLM이 이를 한 줄 노트로 바꾼 뒤 재요약한다. 작업 영역에 "지식과 경험이 축적"된다는 서술에 비해 실제 축적은 사건당 한 줄이다. MVP로는 충분하지만 문항 1의 서술은 그보다 크다.
  4. **계약은 `review` 역할만** 받는다(`_check`: `role != "review"` → "unsupported role"). "역할을 부여하는 계약"이라는 일반 서술은 구현보다 넓다.
  5. 로그 28행: `find("이 공모의 심사자")`가 심사 역할을 공개하지 않은 HR·UX peer도 후보로 돌려줬다. 심사자가 1순위였고 `engage`의 `can` 검사가 나머지를 막았으므로 결과는 맞았지만, 맥락 발견이 "offers"를 읽었다는 증거로는 약하다.
- 해결: 신청서에서 "역할 제공 선언은 설정(소유자가 정함), 자기소개 문장은 비서가 요약"으로 둘을 나눠 쓴다. 이것이 오히려 "사람이 통제하는 것"을 분명히 해 보안 시선에 유리하다. `until`은 peer 설정으로 빼고 `call`에도 적용한다. 2일 과제로 "다른 역할(예: 멘토) 계약"을 넣으면 일반성 주장에 근거가 생긴다.

### (4) 해커톤 적합성

**R5-8 [중간][사업·기술] 문항 3이 "2일 동안 구현할 기능"이 아니라 "이미 구현한 기능"의 목록이다(3차 낮음 → 중간, 체크리스트 등재).**
- 근거: 문항 3 서두("사전 검증으로 … 한 번 끝까지 실행했습니다")와 1~9번 목록(전부 구현됨), 문항 2-6 "구현했습니다", proposal-notes의 2일 일정(M1~M8, 구 시나리오).
- 해커톤 2일 동안 할 일로 문서가 말하는 것은 "안정화"(3-7)와 "현장 참가자 참여 계획 `[가정]`"(7-6①)뿐이다. 심사위원은 (a) 사전 코드가 허용되는지, (b) 허용된다면 2일에 무엇이 더해지는지를 묻는다. 둘 다 답이 없다. 사전 코드 제한이 있으면 실격 위험이라 주최 측 확인이 필요하다(premises는 "고려하지 않는다"로 두었지만, 신청서는 그 위험을 안고 있다).
- 해결: 문항 3을 "사전 준비(완료)"와 "해커톤 2일(할 것)"로 나눈다. 2일 목록 후보: R3-13 유일성 규칙, 채택 상한 조정과 5건 이상 응모(R5-5), 실제 사람 peer 입력창(R5-7), `until` 만료 장면, 두 번째 역할 계약, 비서 루프 반복 5회 성공률 기록, 대시보드 노드별 LLM/폴백 표시. 사전 코드 허용 여부를 주최 측에 확인해 한 줄 적는다.

**R5-5 [높음][기술] (변동 없음) 시연 숫자의 증거력.** 추가 확인: 로그 33~39행에서 broker가 6명에게 알렸고(프롬프트 하한 "최소 6명"과 같다), 거른 3명 중 1명(312ba0)은 `abstain=True`로 **설정이 강제한 거름**이다. 재량으로 거른 것은 5명 중 2명이고 두 사유 모두 프롬프트에 넣은 `eager` 값을 인용한다(0.6, 0.5). 3건 중 3건 채택, `adoption_rate 1.0`은 그대로다.

### (5) 신뢰 모델과 보안 (변동 없음인 것들)

**R3-4 [높음][기술·보안] (변동 없음)** 수집가 구조는 primary-replica다: 수집가 1이 순서·시각을 부여하고 `replicate`는 **인증 없이** 받으며(`CollectorNode.handle`), 두 노드는 같은 프로세스·같은 운영자다. 문항 7-3은 "수집가 둘의 공모"를 비보장으로 적지만 "운영자가 같으면 DB와 무엇이 다른가"에는 여전히 답이 없다. 문항 4가 원장을 "분쟁 대비 증거"로 세운 만큼 이 질문의 무게가 커졌다. 2일 안에 할 수 있는 최소 답: 수집가 2를 별도 프로세스로 띄우고 `replicate`에 수집가 1의 서명을 요구하며, "실제 도입에서는 감사 부서와 IT 부서가 각각 운영"을 한 줄로 쓴다.

**R2-7, R2-8, R2-6, R1-7 (🟡로 조정)** 위 표 참조. 공통점은 **문서는 정직해졌지만 메커니즘은 그대로**라는 것이다. 실서비스 축이 4점에 머무는 이유다.

**R2-9 [중간][보안]** 삼성SDS클라우드 Simple AI Inference는 공식 페이지에서 "OpenAI API 호환, 프라이빗·퍼블릭 엔드포인트, 고객 데이터를 외부 모델 학습에 쓰지 않음"까지 확인했다. 프롬프트·출력의 보존 기간과 로그 정책은 페이지에 없어 **미확인**이다. 신청서는 이 서비스가 **자사/사내 허용 서비스인지**를 말하지 않는다. 만약 그렇다면 7-5의 "전제"를 사실로 바꿀 수 있는 가장 쉬운 보강이다. Claude API 경로(`claude-opus-5-5`)는 모델 ID가 실재함을 이번에 확인했지만(3차 미확인 해소), 외부 서비스라는 점은 변함없다.

## 4. 잘된 점

- **선등록 순서를 실제로 고쳤다.** `PeerAgent.work`가 publish → submit → share 순서이고, a2a-transaction 3절 흐름도와 7-3 서술("보내기 전에 선등록")이 코드와 일치한다. 3차의 가장 큰 기술 결함이 해결됐다.
- **증거를 저장소에 넣었다.** `review/evidence/live-run-gpt-oss-120b.txt`가 있어 신청서의 숫자를 대조할 수 있게 됐다. 이번 지적(R3-13, R3-14)은 바로 그 덕에 가능했다. 증거 제출 자체는 올바른 방향이다.
- **위촉 계약을 원장 규칙으로 강제한다.** `_check`가 `feedback(review)`에 같은 `call_id`의 `contract`를 요구한다. "계약 없는 심사는 기록되지 않음"(문항 1)은 코드로 확인된다.
- **근거 문서 3개가 구현 기준으로 다시 쓰였다.** broker-and-discovery 3절("임베딩·필드 필터는 구현하지 않음", "최소 6명 지침이라 선택 수는 품질 증거가 아님")과 a2a-transaction 1절은 3차 지적을 그대로 받아들여 과장을 걷어냈다.
- **한계 서술이 더 정직해졌다.** 7-4(인증 미구현, 프로필 준식별자, 주소 노출), 7-5(주입 방어 미구현), 7-6⑥⑦(자기 요약의 진위, 루프 불안정). 문항 4의 "분쟁 대비 증거" 재정의도 R1-6에 대한 성실한 답이다.
- **파서 수정과 폴백 설계.** `llm._parse`가 첫 JSON 객체만 읽어 여분 출력에 견디고, 모든 호출이 폴백을 가져 시연이 멈추지 않는다.

## 5. 권고 (우선순위)

1. **증거를 신청서에 맞추지 말고 신청서를 증거에 맞춘다.** 로그에 시각을 넣어 다시 실행·저장하고, 문항 2-1("중복 요청" → "첫 호출 인자 오류 후 재시도 성공"), 2-2(예시 교체), 3("제출 4명" → "제출 3명 + 심사자 1명", 시간, 원장 건수)을 로그 그대로 고친다(R3-14).
2. **원장에 심사 유일성 규칙을 넣는다**(evaluator × content_hash × call_id). 30분 작업이고, 넣지 않으면 "분쟁 대비 증거"라는 문항 4의 주장이 로그 한 줄에 무너진다(R3-13).
3. **문항 3을 "사전 준비(완료)"와 "해커톤 2일(할 것)"로 나누고**, 사전 코드 허용 여부를 주최 측에 확인한다(R5-8). 2일 목록에는 R5-5 해결(5건 이상 응모, 채택 상한 2), 실제 사람 peer 1~3명(R5-7), 수집가 2 별도 프로세스 + replicate 서명(R3-4)을 넣으면 가장 아픈 질문 세 개가 "해커톤에서 보여 줄 것"으로 바뀐다.
4. **역할 제공은 설정, 자기소개는 비서 요약**으로 나눠 쓴다(R3-15). 과장을 줄이면서 "사람이 통제하는 지점"이 생겨 보안 시선에서 점수가 난다.
5. 7-3의 보장 서술을 "바이트 동일 해시", "수집가가 부여한 순서와 시각"으로 낮추고(R3-11 잔여), 문항 1 헤드라인의 "대화로"를 "서로 호출하고"로 바꾼다(R3-10).
6. stale 참조를 고친다: system-overview 6절 8단계, 10절 실행 방법, 1절 스택, broker-and-discovery 6절 M7, README 문서표, premises의 broker 연합·파생(R3-12).
7. 기존 제품 비교 한 줄(R4-1, R4-3)과 7-5에 "Simple AI Inference가 사내 허용 서비스인지"를 사실로 쓴다(R2-9).
