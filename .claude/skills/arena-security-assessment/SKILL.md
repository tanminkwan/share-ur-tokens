# arena-security-assessment: 인터넷 노출 보안 진단

결과물은 `docs/security-assessment.md` 한 편이다. 읽는 사람은 **플랫폼을 인터넷에 띄우려는 운영자**와 **플랫폼을 고치는 개발자**다. 운영자는 "무엇을 막고 어떻게 배치해야 하나"를, 개발자는 "무엇을 코드로 고쳐야 하나"를 얻어야 한다.

## 무엇을 하고 무엇을 하지 않나

| 한다 | 하지 않는다 |
|---|---|
| 노출면(포트, 공개 API, 사람의 창)을 정리하고, 통상적인 취약점 범주마다 지금 상태를 **저장소에서 확인**한다 | CVE 목록 대조, 의존성 버전 스캔, 코드 줄 단위 감사, 침투 시험 |
| 범주마다 위험 등급과 조치(운영자 / 플랫폼)를 적는다 | 확인하지 않은 것을 확인한 것처럼 쓰기 |
| 이미 있는 방어(서명, 원장 규칙, 토큰, 봉투)를 공정하게 적는다 | 겁주기, 과장("치명적", "완전히 뚫림"), 안심시키기("안전하다") |

## 절차

1. **전제를 적는다.** 어떤 배치를 가정하나(기본: broker·recorder·peer의 A2A·API 포트가 인터넷에 열림, TLS 없음, 기본 설정). 사용자가 다른 배치를 말하면 그것을 쓴다.
2. **노출면을 모은다.** 포트와 서비스는 `docs/internal-network-test.md` 2절과 `arena/config.py`(`*_PORT`, `*_HOST`)에서, 공개 API는 `dev/protocol.md` 4.1·5절과 `arena/recorder/api.py`, `arena/broker/api.py`에서, 사람의 창은 `arena/bundled/*/api.py`에서 확인한다. Mermaid 그림 하나로 그린다.
3. **범주마다 확인한다.** `references/checklist.md`의 범주와 "확인할 곳"을 따라 코드·설정을 직접 grep하고 읽는다. 확인한 사실에는 파일 경로를 단다. 확인하지 못한 것은 "확인 안 됨"으로 쓴다.
4. **등급을 매긴다.** `references/checklist.md`의 등급 기준(높음·중간·낮음)을 쓴다. 등급은 "인터넷 노출이라는 전제에서" 매긴 것임을 밝힌다.
5. **조치를 둘로 나눈다.** ① 운영자가 **코드를 고치지 않고 지금** 할 수 있는 것(배치, reverse proxy, 방화벽, 설정 값), ② 플랫폼이 고칠 것(코드 개선 후보, 번호 `SEC-n`). 설정으로 되는 것은 설정 키 이름을 정확히 적는다(`.env.example`에서 확인).
6. **배치 권고 그림**을 하나 그린다(인터넷 → TLS·빈도 제한 앞단 → 서비스, 사람의 창은 VPN·SSH 안쪽, god 키는 오프라인, 밖으로 나가는 요청은 egress 제한).
7. **우선순위 표**로 끝낸다: 공개 전 반드시, 공개 직후, 나중.
8. **한계**를 적는다: 이 진단이 보지 않은 것(코드 감사, 의존성 취약점, 침투 시험, 법률·개인정보 판단).

## 쓰는 규칙

- 그림은 Mermaid로만. 기술 용어는 영어 그대로(TLS, reverse proxy, rate limit, SSRF, token). 만든 한국어 말(칸, 판, 봉투)은 쓰지 않는다.
- 문장은 짧은 평서문. 범주마다 **현황 → 위험 → 조치** 순서.
- 날짜를 적는다(진단 기준 커밋도). 코드가 바뀌면 진단도 낡는다.
- 갱신할 때는 기존 문서를 읽고, 바뀐 범주만 고치고, 고친 범주의 상태(해결됨·남음)를 표에 표시한다.
- 해결된 항목은 지우지 않고 "해결됨(날짜, 커밋)"으로 남긴다.
