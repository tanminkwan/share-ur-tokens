# 신청서 작성 가이드 (7개 문항)

문항 제목과 순서는 주최 측 양식이며 바꾸지 않습니다. 이 가이드는 각 문항에 **무엇을 담아야 점수가 나오는지**를 정리한 것입니다. 점수 축 이름은 `proposal-reviewer/references/criteria.md`와 같습니다.

| # | 문항 | 주로 걸리는 축 | 반드시 담을 것 | 흔한 감점 |
|---|---|---|---|---|
| 1 | AI로 해결하고자 하는 문제 상황 또는 새롭게 시도해보고 싶은 업무/서비스 | 비즈니스 임팩트, 독창성 | 문제 2~3개(누가 겪고, 지금은 어떻게 하는가), 새 서비스의 한 단락 요약, 기존 방식과의 차이 | 가상의 문제, 대상 사용자 없음, 기술 소개로 시작 |
| 2 | AI를 어떻게 활용할 계획인가 | AI 활용도 | AI가 맡는 핵심 역할과 그 이유, AI 없이 되는 부분의 구분, 개발과 시연에서의 AI 활용 | "AI로 효율화" 같은 추상 서술, AI가 장식인 구조 |
| 3 | 2일 동안 구현할 주요 기능 | 실현가능성(MVP), 발표·시연 | 번호 붙은 기능, 시연 시나리오 한 편, 구현하는 것과 말로만 설명하는 것의 경계 | 2일에 불가능한 범위, 시연이 안 보이는 기능 나열 |
| 4 | 주요 사용자와 기대효과 | 비즈니스 임팩트 | 사용자 유형별 이유, 기대효과와 **측정 방법** | 출처 없는 수치, "모든 임직원" |
| 5 | 구현된 모습 한 줄 요약 | 발표·시연, 독창성 | 사용자가 겪는 장면 한 문장. 기술 용어 최소화 | 두 줄 이상, 기능 나열 |
| 6 | [선택] 필요한 데이터 | 실현가능성(MVP), 보안 | 데이터 항목, 위치, 포맷, 필요한 환경과 권한. 사내 데이터를 쓰면 반출 여부 | 비워 둠, 외부 서비스에 사내 데이터를 보내는 구조 |
| 7 | 추가 언급 | 실현가능성(실서비스), 보안, 독창성 | 알고 있는 한계와 대응책, 보안·규정 설계, 확장 방향 | 한계를 숨김, 문항 1~4의 반복, 과장 |

## 문항 간 역할 분담

- 1은 **왜**, 2는 **AI가 무엇을**, 3은 **2일에 무엇을**, 4는 **누가 쓰고 무엇이 달라지는가**, 7은 **현실의 벽과 대응**입니다. 겹치지 않게 씁니다.
- 숫자와 주장은 한 곳에서만 정의하고, 다른 곳은 같은 값을 씁니다.

## 문장 규칙

- 근거 없는 절대 표현을 쓰지 않습니다("완벽", "100%", "원천 차단", "무결점", "세계 최초").
- 확인하지 못한 사실은 `[가정]` 또는 "미확인"으로 씁니다. 지어낸 수치를 쓰지 않습니다.
- 효과는 "줄어듭니다"로 끝내지 않고 **무엇으로 재는지**를 함께 씁니다.
- 용어는 `review/premises.md`의 정의를 씁니다(peer, broker, 노출, 답변지 등). 같은 대상을 다른 말로 부르지 않습니다.
- 사내 데이터와 외부 AI 서비스 사이의 흐름은 반드시 명시합니다.

## 심사위원이 던질 단골 질문 (신청서에 답이 있어야 함)

1. 사내 게시판, 검색, 장터와 무엇이 다른가? → 문항 1, 7
2. AI가 없어도 되는 것 아닌가? → 문항 2
3. 2일 안에 정말 되는가, 무엇이 가짜(하드코딩)인가? → 문항 3
4. 공급자는 왜 응하는가, 콜드 스타트는? → 문항 7
5. 사내 보안 정책을 통과하는가, 데이터는 어디로 가는가? → 문항 6, 7
