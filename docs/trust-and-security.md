# 신뢰와 보안

## 1. 신원

- 임직원 인증(사내 SSO)을 거친 소유자만 peer를 등록할 수 있습니다.
- 각 peer는 소유자와 연결된 식별자를 가지며, 메시지에 서명합니다. broker는 서명을 확인해 사칭을 막습니다.
- MVP는 SSO 연동 대신 사전 발급한 키를 쓰고, 한계로 명시합니다.

## 2. 신뢰 문제와 대응

| 위험 | 설명 | MVP의 대응 | 남는 한계 |
|---|---|---|---|
| 허위·과장 노출 | 줄 수 없는 것을 노출한다 | 노출에 소유자와 유효 기간을 붙이고, 거래 후 소비자가 신고할 수 있다 | 진위를 자동 검증하지 못한다 |
| 스팸 노출 | 같은 노출을 반복 등록한다 | peer당 노출 개수와 등록 빈도를 제한한다 | 의미만 바꾼 우회 |
| 사칭 | 다른 사람의 peer인 척한다 | 서명 확인 | 키 유출 시 무력 |
| broker 편향 | 특정 peer를 상위에 올린다 | 일치 근거를 답변지에 함께 보여 준다 | broker 운영자를 믿어야 한다 |
| 프롬프트 주입 | 노출·요청 텍스트에 에이전트 지시문을 섞는다 | 외부 텍스트를 지시가 아니라 데이터로만 취급하는 프롬프트 구성, 권한 범위 제한 | 완전한 방어는 불가능하다 |
| 에이전트 오판 | 협상 중 잘못된 조건에 합의한다 | 자동 확정 권한 범위와 횟수 상한 | 해석 오류 자체 |

## 3. 사내 보안과 규정

- **데이터 반출**: 노출과 요청은 사내 정보를 포함할 수 있습니다. broker와 LLM 호출은 **사내망 안**의 허용된 LLM만 씁니다. 외부 LLM으로 사내 데이터를 보내지 않습니다.
- **노출 범위**: 노출에는 공개 범위(전사, 부서, 지정 대상)를 달 수 있습니다. broker는 범위 밖 요청자에게 답변지에 넣지 않습니다. MVP는 전사 공개만 구현합니다.
- **개인정보**: 노출에 개인정보(연락처 등)를 넣지 않도록 입력 단계에서 안내하고 간단한 패턴 검사를 합니다. 완전한 탐지는 하지 않습니다.
- **p2p 연결**: 에이전트는 개인 PC가 아니라 사내 서버나 컨테이너에서 돌게 해 인바운드 연결 문제를 피합니다. 서버 간 직접 호출이 보안 정책에서 허용되는지는 확인이 필요합니다(미확인). 허용되지 않으면 broker가 메시지를 중계하는 방식으로 후퇴하며, 그때 "거래는 peer 직접"이라는 원칙은 성립하지 않습니다.
- **책임 소재**: 에이전트가 확정한 거래의 책임은 peer의 소유자에게 있습니다. 확정은 소유자가 취소할 수 있고, 양쪽 peer가 시각, 당사자, 조건, 결과를 로그로 남깁니다. broker는 거래 내용을 보관하지 않으므로 거래의 책임 주체가 아닙니다.
- **감사 기록**: 거래의 당사자와 결과만 각 peer가 보관합니다. 감사 요구가 있으면 최소 로그(시각, 당사자, 결과)를 제공할 수 있게 합니다.

법률·사내 규정의 최종 판단은 법무와 정보보안 부서의 확인이 필요합니다.
