# 신청서 작성 메모 (제출 대상 아님)

`hackathon-proposal.md`는 제출용이라 내부 판단과 미해결 과제는 여기에 둡니다.

## 사용자 확인이 필요한 가정

`review/premises.md`의 `[가정]` 항목 전부. 특히 다음 세 가지가 신청서의 방향을 정합니다.

1. 데모 도메인: 이벤트 + 물품 대여로 두었다. 다른 도메인이 더 설득력 있는가?
2. 대가의 형태: 무상 제공과 교환만 다룬다. 포인트나 금전은 범위 밖이다.
3. 사내망에서 p2p 직접 연결이 허용되는가? 허용되지 않으면 문항 7의 "거래는 peer 직접" 주장이 약해진다.

## 예상 질문과 현재 답

| 질문 | 현재 답 | 신청서 위치 |
|---|---|---|
| 사내 게시판·검색과 무엇이 다른가 | 발견에서 끝나지 않고 연결과 협상까지 에이전트가 수행한다 | 문항 1, system-overview 5절 |
| 왜 broker가 필요한가, 전부 p2p로 하면 안 되는가 | 서로 모르는 상태에서 탐색할 방법이 필요하다. 발견만 broker, 거래는 직접 | 문항 1, 7 |
| 공급자가 왜 응하는가 | **미해결.** 무상·교환만 다룬다 | 문항 7 ③ |
| 허위 노출은 어떻게 막는가 | 자동 검증 불가. 소유자 식별, 빈도 제한, 신고로 완화 | 문항 7 ① |
| 사내 보안 정책을 통과하는가 | 사내 허용 LLM만 사용. p2p 허용 여부는 미확인 | 문항 6, 7 |

## 미해결 과제

- 사내 기존 도구(게시판, 지식 관리, 사내 장터)와 외부 유사 서비스 조사. 현재 차별점은 조사 없이 쓴 것이다.
- a2a 표준의 사양과 버전 확인. 구현 방식 결정.
- 비즈니스 임팩트의 정량 추정 근거. 현재는 측정 방법만 제시한다.
- 해커톤 주최 측의 실제 심사표 확인. 현재 기준은 공개 사례의 공통 경향이다.

| 시간 | 작업 |

| 1일차 오전 | 메시지 스키마 확정, peer·broker 뼈대, 시드 데이터 |
