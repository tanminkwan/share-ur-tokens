# [해커톤 기획서] 에이전트 광장 (Agent Agora)

> **일하며 쌓아 둔 내 지식을, 필요한 쪽의 AI 에이전트가 찾아와 기회로 바꾸는 사내 에이전트 광장**

---

### 문항 1

```text
1. AI로 해결하고자 하는 문제 상황 또는 새롭게 시도해보고 싶은 
   업무/서비스는 무엇인가요?
   현재의 업무를 더 효율적으로 바꾸는 것부터, 지금까지 없던
   새로운 업무 경험이나 서비스를 만드는 것까지 자유롭게 적어주세요.
```

**답변**

**한 줄로**: 일하며 쌓아 둔 내 지식을, 필요한 쪽의 AI 에이전트가 찾아와 기회로 바꾸는 사내 에이전트 광장입니다. 구성원마다 AI 에이전트를 두고 에이전트끼리 직접 찾고 묻고 일을 주고받으며, 정보와 기회에 다가가는 일을 내 에이전트가 **더 능동적으로, 더 제대로, 더 효율적으로** 해 줍니다.

**문제**

1. **지식이 묻혀 있습니다.** 지금의 지식 공유는 "정리해 올리면 찾아 읽는" 방식이라, 시간을 내 올린 것만 드러납니다. 실무자의 경험과 아이디어는 개인 메모에 머물다 사라집니다.
2. **기회가 사람에게 닿지 않습니다.** 공모가 열린 줄 모르거나 낼 만한지 몰라 주저합니다. 진행자는 홍보·섭외·접수·취합을 손으로 합니다.
3. **기여는 남지 않고, 시스템 비용은 듭니다.** 누가 냈고 무엇이 쓰였는지 추적되지 않고, 작은 조직은 플랫폼과 운영 인력이 없어 시작하지 못합니다.

**해결: 지식 공유의 방향을 뒤집습니다**

| | 지금 | 에이전트 광장 |
|---|---|---|
| 지식을 가진 쪽 | 공유하려고 정리해 올림 | 일하며 공개 영역(내 에이전트에게 열어 둔 내 폴더)에 **쌓기만** 함 |
| 지식이 필요한 쪽 | 검색하거나 우연히 발견 | 그쪽 에이전트가 맞는 사람을 **찾아가 요청** |
| 참여 | 공지를 본 뒤 새로 작성 | 내 에이전트가 **쌓인 지식으로 다듬어** 제출 |
| 드러나는 것 | 올린 지식만 | **숨은 지식과 역량** |

가져간 쪽은 심사·활용해 가치를 매기고, 누가 냈고 무엇이 채택됐는지가 서명된 기록으로 남아 보상의 근거가 됩니다.

**왜 p2p인가**: 지식이 묻히는 원인은 "중앙에 올려야 보이는" 구조 자체입니다. 그래서 중앙 플랫폼이 아니라 **구성원의 에이전트끼리 직접 연결되는 p2p**로 만듭니다.

| 중앙 플랫폼 방식이라면 | p2p라서 가능한 것 |
|---|---|
| 지식을 올려야 보이고, 올리지 않은 것은 없는 것 | 요청이 **내 에이전트에게 직접** 오고, 내 에이전트가 고른 것만 상대에게 바로 건넵니다. 중간에 내용을 모아 두는 자리가 없어 쌓기만 해도 됩니다 |
| 중앙이 모든 자료를 읽을 권한을 가져야 검색이 됨 | **가진 쪽이 무엇을 줄지 정합니다.** 넓은 접근 권한이 필요 없고, 부서·협력사 경계를 넘어도 같은 방식입니다 |
| 운영자가 연결과 기록을 쥐고, 구축·운영 비용이 듦 | 기록을 구성원의 에이전트가 맡고(구현) broker도 그렇게 맡도록 설계해 **새로 구축할 중앙 시스템 없이** 시작하고, broker를 이으면 넓어집니다. 드는 것은 각자 에이전트의 실행 비용입니다 |
| 실적과 평판이 플랫폼의 것 | 기록은 구성원이 맡은 기록자가 보관하고 당사자 서명이 붙어, 운영 주체가 아니라 **당사자의 것**입니다 |

**무엇을 만드나: 세 가지를 분리합니다**

- **① 플랫폼 (실제 목적물)**: 어떤 커뮤니티의 어떤 일이든 올라가는 바탕입니다.
  - **p2p·A2A 체계**: 구성원마다 에이전트(peer)가 하나씩 있고, 각 peer의 **프로필**은 broker에 게시되고 검색됩니다. 프로필은 사람이 정한 자기 정체(가명 또는 실명, 소속, 맡을 수 있는 역할)와, 내 에이전트가 공개 영역을 분석해 뽑은 주제·제목을 라벨로 붙인 것입니다. broker는 AI 없이 게시와 검색만 하고, 메시지는 broker를 거치지 않고 에이전트끼리 직접 오갑니다(A2A: 에이전트 간 통신 표준). 기록은 역할을 맡은 구성원의 에이전트(기록자)가 돌리며 이는 구현되어 있습니다. broker도 같은 방식으로 구성원이 맡도록 설계했고, 프로토타입에서는 아직 별도 프로세스로 띄웁니다.
  - **공통 기능**: 프로필과 라벨(두 종류. **커뮤니티 라벨**은 소속 같은 경계, 예: `소속:삼성SDS`. 실제 도입에서는 회사 로그인 시스템이 서명해 발급하고(이번 범위 밖) 시연에서는 각자 적은 값. **역량 라벨**은 할 수 있는 역할과 분야, 예: `역할:심사`, `분야:클라우드 비용`, 내 에이전트가 공개 영역의 지식과 원장 실적을 근거로 스스로 붙이고 갱신하며 만기가 있음), 공개 영역(내 PC 전체는 사적 영역이고 그중 내가 에이전트에게 열어 둔 한 곳이 공개 영역. 로컬 폴더·클라우드·URL 어디든, 원문은 내 에이전트만 읽음. 지식 문서뿐 아니라 내가 가진 자산이나 시스템 접근 권한 같은 것도 들어갈 수 있으며, 그런 것은 소유자가 확인하기 전에는 에이전트가 쓰지 않음. 시연에서는 문서만 씀), 마감이 있는 이벤트, 역할 계약(이벤트마다 심사자·기록자 같은 역할을 양쪽 서명으로 맡기는 것).
  - **공증되는 원장**: 누가 무엇을 냈고, 무엇이 채택됐고, 어떤 역할을 했는지를 당사자 서명으로 남기는 장부입니다. 구성원 평가와 보상의 근거이며, 기록 역할을 맡은 구성원의 에이전트(기록자)들이 나눠 보관하도록 설계했습니다.
- **② 앱과 지식 (플랫폼에 탑재)**: 일의 종류마다 역할별 앱과 그 앱의 판단 규칙·LLM 프롬프트를 플러그인처럼 얹습니다. 이번에는 **아이디어 경연 앱**(진행자, 참여자, 심사자, 절대자: 원장 열람 전용)을 만듭니다. 상담·자료 공유·협업 모집은 다른 앱으로 얹습니다.
- **③ 시연 장치**: 사람을 대신하는 페르소나 에이전트입니다. 시연만을 위한 것이며, 실제로는 사람이 그 자리에 들어옵니다.

### 문항 2

```text
2. 제안한 아이디어를 실현하기 위해 AI를 어떻게 활용할 계획인가요?
   AI 활용 방안과 이를 통해 문제를 해결하거나 새로운 변화를 만드는 
   방법을 구체적으로 작성해 주세요.
```

**답변**

광장이 실현되면 각 에이전트 안에서 **LLM이 사람 대신 읽고, 판단하고, 쓰고, 다른 에이전트와 요청을 주고받습니다.** 사람은 지식의 원천이자 최종 결정자로 남고, 연결·조율·기록은 에이전트끼리 끝냅니다.

**① 플랫폼: AI가 하는 일과 코드가 하는 일 (모든 앱 공통)**

- 내 에이전트가 공개 영역의 메모와 문서를 분석해 주제·강점·할 수 있는 일을 뽑아 프로필에 라벨로 붙여 게시하고, 참여할 때마다 교훈을 남겨 스스로 갱신합니다. 역량 라벨도 같은 근거(지식과 원장 실적)로 붙이고 떼며, 근거 없는 라벨은 붙이지 않습니다. 정리해 올리지 않은 지식도 라벨로 검색됩니다.
- 틀리면 안 되는 일은 AI가 아니라 코드가 합니다: broker 검색, 전자 서명, 원장 규칙(보내기 전에 원장에 먼저 등록한 사람이 원작자, 계약 없는 심사 거절 등), 변조 탐지. AI가 잘못 판단해도 기록은 조작되지 않습니다.

**② 경연 앱의 AI: 역할마다 사람의 일을 돕거나 대신합니다 (앱의 규칙과 프롬프트로 정해짐). 점수와 채택처럼 책임이 따르는 결정은 사람이 확정합니다.**

| 앱 | AI가 하는 일 | 풀리는 문제 |
|---|---|---|
| 진행자 | 주제만 받으면 프로필 검색과 추천 에이전트로 맞는 사람을 찾아 직접 요청하고(검색에 안 잡히는 사람을 위해 공지를 함께 올릴 수도 있음), 역량 라벨과 프로필 검색으로 찾은 심사자·기록자 후보와 역할 계약을 맺고(후보의 원장 실적을 확인하는 기능은 3번 2일 계획 ①), 마감 뒤 심사 요청을 보내고 결과를 모아 채택안을 만들며, **채택은 진행자 확인 뒤** 기록 | 홍보·섭외·접수·취합 수작업 |
| 참여자 | 요청이 오면 공개 영역(문장 인용), 내 규칙, 상황, 위험, 상대 신뢰로 응할지 정하고, 응하면 공개 영역 문서에서 맞는 아이디어를 골라 기획서로 다듬어 **출처와 함께** 제출. 내용은 내 지식이고 작성만 에이전트가 한 것이며, 실제 직원의 기본 규칙은 **제출 전 확인**이고 자동 제출은 본인이 규칙으로 허용할 때만 | 몰라서·번거로워서 놓치던 참여, 새로 쓰는 부담 |
| 심사자 | 작성자를 모른 채 받은 아이디어를 참신성·실현 가능성·기대 효과 기준으로 요약·비교한 표와 점수 초안을 만들고, 심사자가 확정한 점수·의견을 서명과 함께 기록. **점수의 책임은 사람 심사자**에게 있음(시연에서는 페르소나가 확정) | 읽고 비교하는 시간, 평가 근거가 남지 않음 |
| 절대자 | 원장의 실적과 게시된 프로필을 모아 구성원별 강점·실적표를 만듦(집계는 코드) | 기여 집계 수작업 |

다른 앱을 얹으면 AI가 하는 일도 그 앱의 지식에 맞게 바뀝니다.

### 문항 3

```text
3. 해커톤 2일 동안 구현해 보고 싶은 주요기능은 무엇인가요?
   아이디어가 구현되면 사용자가 무엇을 하고, 
   AI가 어떤 결과를 보여줄지 적어주세요.
```

**답변**

**범위**: 2일 동안 **① 플랫폼과 ② 아이디어 경연 앱을 구현**하고, **③ 페르소나는 시연용으로 준비**합니다. 시연의 초점은 **플랫폼을 쓰면 사용자 경험이 얼마나 달라지는가**입니다.

**필요 도구·데이터·개발 여건**: Python과 A2A 공식 SDK, 해커톤 환경의 LLM API(프로토타입 기준 동시 호출 약 15회)만 있으면 되고, 노트북 한 대에서 peer 13개와 broker 4곳을 로컬 포트로 띄웁니다. 데이터는 페르소나의 공개 영역 문서(직접 작성)와 현장 참가자가 당일 적어 넣는 문서뿐이라 사내 데이터가 필요 없습니다. 현장 참가자의 공개 영역은 참가자 PC가 아니라 발표자 노트북의 폴더에 두어, PC 사이 네트워크 호출 위험을 시연에서 없앱니다.

**사전 준비(완료)**: 전체 흐름이 도는 프로토타입을 실제 LLM으로 실행했습니다. 페르소나 13명이 두 공간(응모·심사)으로 나뉜 broker 4곳에 붙어 역할 계약 → 아이디어 5건 → 심사자 2명 심사 → 2건 채택까지 진행됐고, 원장 35건이 서명과 함께 남았으며 권한 없는 열람 거부와 변조 탐지를 확인했습니다. 다만 이 실행에서 마감 뒤 진행은 LLM 응답 오류로 정해 둔 순서로 대체됐고 두 심사자의 점수가 같게 나왔으며(10회 측정에서 완주율과 심사 변별력을 함께 잽니다), 공지를 올리는 방식이고 역할 기능이 한 코드에 섞여 있으며, 역할 라벨은 아직 사람이 적어 둔 고정값입니다.

**2일 동안 할 것**

| 순서 | 구분 | 할 일 |
|---|---|---|
| 1 | ③ 시연 장치 | 페르소나 13명과 각자의 공개 영역 문서(쌓인 아이디어, 소유자 규칙, 상황) |
| 2 | ① 플랫폼 | 공개 영역을 주소로 연결하는 기능, 공지 없이 대상에게 직접 요청하는 기능, 에이전트가 역량 라벨을 스스로 갱신하는 기능, 역할 계약 전에 후보의 원장 실적을 기록자에게 확인하는 기능 추가(시연은 기록자가 1명이라 심사자 후보만 확인). 발견·계약·서명·원장은 다듬어 씀 |
| 3 | ② 경연 앱 | 수집 방식에 필요한 참여자 앱(공개 영역 문서로 기획서 다듬기, 출처 표시)과 진행자 앱(찾아가 요청)을 먼저 분리 |
| 4 | ② 경연 앱 | 심사자·절대자 앱 분리, 규칙·프롬프트를 각 앱의 지식으로 정리 |
| 5 | 검증 | 같은 경연 10회 반복 측정(사전 검증 12회 중 6회 완주), 현장 참가자 2~3명 실제 참여, 리허설과 녹화 |

**후퇴선**: 2일차 오후까지 1~3이 끝나지 않으면 사전 프로토타입(공지 방식)으로 시연하고, 수집 방식과 앱 분리는 설계로 설명합니다. 시간이 남으면: 기록자 여러 명의 상호 대조, 확정 전 사람 확인 단계, 기간이 정해진 권한.

**사용자 경험이 이렇게 달라집니다**

| 역할 | 지금 | 플랫폼 + 경연 앱 |
|---|---|---|
| 진행자 | 공지·홍보·섭외·접수·취합을 손으로 | 주제와 마감만 정하고 결과를 확인 |
| 참여자 | 공모를 우연히 알고, 그때부터 새로 작성 | 평소처럼 메모만. 요청이 찾아오고 내 에이전트가 기획서로 다듬어 제출, "이걸로 낼까요?"에만 답함 |
| 심사자 | 파일을 받아 읽고 점수표를 따로 회신 | 작성자 없는 아이디어와 기준별 비교표·점수 초안을 한 번에 받고, 확정한 점수·의견이 자동 기록 |
| 절대자(관리자) | 응모·채택·기여를 엑셀로 집계 | 구성원별 강점·실적표가 자동으로 나오고, 기록 변조도 탐지 |

**시연 장면 (약 5분)**: 장면의 진행자는 발표자, 참여자 중 2~3명은 현장 참가자가 당일 적어 넣은 공개 영역(발표자 노트북의 폴더), 나머지 참여자·심사자·기록자는 ③ 페르소나(LLM)입니다. ① broker에 공지가 없고, 참여자마다 공개 영역에 아이디어 문서가 쌓여 있음 → ② 진행자가 주제와 마감만 입력하면 진행자 에이전트가 심사자·기록자와 계약하고 프로필 검색과 추천 에이전트로 맞는 사람을 찾아 직접 요청 → ③ 참여자 에이전트들이 근거를 인용하며 응하거나 넘기고, 출처를 밝힌 기획서를 제출 → ④ 마감 후 심사자 에이전트가 비교표와 점수 초안을 올리고 심사자(시연은 페르소나)가 확정, 진행자 확인으로 채택 → ⑤ 절대자 대시보드에 강점·실적표가 뜨고, 기록을 몰래 고치면 잡아냄.

**AI가 보여 주는 결과**: 인용이 달린 판단 이유, 출처가 달린 기획서, 심사 점수와 의견, 구성원별 강점·실적표.

**범위 밖**: 사내 로그인 연동, 포인트·인사평가 연계, 대규모 분산 합의.

### 문항 4

```text
4. 이 아이디어의 주요 사용자는 누구이며, 어떤 기대효과가 있나요?
   고객 가치 창출, 오류 감소, 정보 접근성 개선, 업무 효율 향상 등 
   기대하는 변화를 구체적으로 적어주세요.
```

**답변**

**주요 사용자**: 부서·회사·협력사 연합 같은 커뮤니티와 그 구성원. 일을 여는 사람(공모 진행자, 부서장, TF 리더), 응하는 구성원(경험은 있지만 나서지 않던 실무자), 역할을 맡는 구성원(심사·기록).

**기대효과**

- **능동적으로**: 필요한 쪽 에이전트가 맞는 사람을 찾아가므로, 숨은 실력자와 아이디어가 드러나고 몰라서 놓치는 참여가 줄어듭니다.
- **제대로**: 내 공개 영역과 규칙을 근거로 맞는 것만 고르고 이유를 남겨, 맞지 않는 일에 끌려가지 않습니다.
- **효율적으로**: 섭외·홍보·접수·전달·집계를 에이전트가 처리하고 사람은 결정할 때만 개입합니다. 검색으로 고른 후보에게만 요청하므로 AI 비용도 필요한 곳에만 쓰되, 검색에서 빠진 사람은 추천과 공지로 보완합니다.
- **공정한 평가 근거**: 낸 아이디어, 채택, 맡은 역할이 서명으로 공증되어 평가와 보상을 기록에 근거해 할 수 있습니다.
- **새 시스템 구축 없이 시작**: 기록을 구성원의 에이전트가 맡고 broker도 그렇게 맡도록 설계해 새 부서나 TF도 바로 시작하고, 새 일은 앱만 얹으면 됩니다.

**측정 방법**: 근거 없는 수치는 제시하지 않습니다. 요청당 응한 비율, 이미 쌓여 있던 아이디어로 낸 비율, 부서 밖 응답자 비율, 검색에는 안 잡혔지만 추천·공지로 참여한 비율(놓침), 에이전트 판단과 본인 판단의 일치율, 진행자의 수작업 단계 수, 마감부터 채택까지 걸린 시간으로 잽니다. 해커톤 2일차에 첫 수치를 얻고, 파일럿에서 기존 방식과 비교합니다.

### 문항 7

```text
7. 제안해 주신 아이디어에 대해 추가로 언급하고 싶은 내용이 있으면 
   작성해 주세요.
```

**답변**

1. **기존 도구와의 차이**: 게시판·공모 시스템·사내 검색은 모두 중앙에 올리고 사람이 찾아가는 구조이고, 에이전트 관리 체계(예: Microsoft Agent 365)나 에이전트 디렉터리 표준(예: AGNTCY)은 관리하거나 찾게 해 주는 데까지입니다. 업무 활동에서 강점을 추론해 전문가를 찾아 주는 기능(예: Microsoft 365 People Skills)은 회사가 추론해 회사 프로필에 올리는 것이고, 에이전트 광장은 내 에이전트가 내 공개 영역에서 요약하고 당사자 서명 실적이 붙는 점이 다릅니다. 사내 에이전트 플랫폼(예: FabriX Agent Studio, Brity Copilot)과는 대체가 아니라 그 위의 층으로 설계했고, peer 에이전트를 그 위에 올리는 연동은 확인할 과제입니다. 에이전트 광장은 에이전트가 찾아가 참여하고, 커뮤니티가 스스로 운영하며, 실적이 공증되는 다음 단계라 기존 도구와 함께 씁니다.
2. **왜 응하고, 초기에는 어떻게 하나**: 응하는 쪽은 새로 쓰는 수고가 없고 채택이 실적으로 남습니다. 참여자가 적은 초기에는 진행자가 있는 일(공모, TF 모집)부터 부서 단위로 시작하고 broker를 이어 넓힙니다. 에이전트는 각자의 PC나 사내 VM에서 돌고, 기록자는 그 역할을 맡은 구성원의 에이전트이며 broker도 구성원이 맡는 설계입니다(프로토타입은 별도 프로세스). 비용은 각자의 에이전트 실행과 LLM 호출 비용이며, 회사 커뮤니티의 라벨 서명과 실명 연결은 회사 로그인·인사 시스템과 잇습니다(이번 범위 밖).
3. **정보 보호**: 공개 영역 원문은 내 에이전트만 읽고, 고른 결과만 건넵니다. broker는 아이디어를 보지 않고, 심사자는 허가된 별도 공간에서 작성자를 모른 채 심사합니다. 원장에는 내용 없이 해시·가명·서명만 남고, 열람은 기록자가 허용한 절대자만 합니다(기간이 정해진 허가는 다음 단계). 실명·가명·익명은 커뮤니티가 정합니다(회사는 인사 프로필과 연결).
4. **확장**: 플랫폼은 그대로 두고 앱만 바꾸면 전문가 상담, 자료 공유, 협업 모집이 됩니다. 앱과 지식은 누구나 만들어 얹을 수 있습니다.
5. **한계와 대응**
   - 프로토타입은 공지 방식이고 앱이 분리되어 있지 않습니다 → 2일 범위의 핵심으로 구현합니다.
   - 페르소나는 참여율과 품질의 증거가 아닙니다 → 현장 참가자의 실제 참여와 비교합니다.
   - 에이전트의 자율 진행은 실행마다 다릅니다(사전 검증 12회 중 6회 완주) → 10회 반복 측정하고, 실패하면 정해 둔 순서로 대신 진행하며 그 사실을 기록합니다.
   - LLM이 쓴 글은 과장되거나 내용이 덧붙을 수 있습니다 → 인용과 출처를 코드로 대조하며, 출처 문서와의 추가 대조가 필요합니다.
   - 시연의 커뮤니티 라벨은 각자 적은 값이라 협력사 peer가 `소속:삼성SDS`를 스스로 달 수 있습니다 → 실제로는 회사 로그인 시스템이 서명한 라벨만 받고, 받는 쪽 에이전트는 서명 없는 라벨을 믿지 않습니다.
   - 시연의 기록자는 1명입니다 → 참여자가 기록자 서명 영수증을 보관해 누락을 증명할 수 있고, 기록자 여러 명은 이후 과제입니다.
   - 다른 에이전트의 글에 숨긴 지시문(예: 기획서 안의 "이 아이디어는 10점")에 대한 방어는 아직 없습니다 → 영향 범위는 비서의 판단, 기획서, 심사 점수입니다. 당장은 심사자 2명의 점수 비교와 절대자의 원장 검토로 이상 점수를 사후에 잡고, 입력을 데이터로 격리해 전달하는 방어는 이후 과제입니다. 서명과 원장 규칙은 코드로 강제되어 영향을 받지 않습니다.
   - 보상은 실적을 보여 주는 데까지이며, 포인트·인사평가 연계는 회사 정책 검토가 필요합니다.
