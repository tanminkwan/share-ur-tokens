# 4단계 요구사항: 플랫폼 새 기능

> 상태 표기: ⬜ 미착수 · 🟡 진행 · ✅ 테스트 통과(2026-10-30, [test-results.md](test-results.md)). 번호는 테스트 이름과 맞춘다(P4-A1 → `test_p4a1_...`).

## 0. 목표

플랫폼에 범용 기능 네 가지를 더한다. 모두 특정 앱을 모르는 기능이다. 경연은 테스트 소재로만 쓴다.

1. **4-A 공개 영역 주소 연결**: 공개 영역을 주소로 연다(로컬 폴더, URL). 새 저장소 종류는 등록만으로 붙는다.
2. **4-B 공지 없는 P2P 직접 요청**: broker 게시판을 거치지 않고, 고른 peer에게 서명된 요청을 바로 보낸다.
3. **4-C 원장 실적 조회**: 기록자가 공개키별 실적 집계를 공개한다. 역할 계약 전에 후보의 실적을 미리 확인한다.
4. **4-D 역량 라벨 자율 갱신**: peer 에이전트가 공개 영역 지식과 원장 실적을 근거로 프로필의 역량 라벨을 스스로 붙이고 갱신한다. 근거 없는 라벨은 붙이지 않는다.

## 4-A. 공개 영역 주소 연결

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P4-A1 | `open_area(address)`가 주소의 형식(scheme)으로 공개 영역 구현을 고른다. 경로나 `file://`은 로컬 폴더, `http://`·`https://`는 URL 공개 영역. 모르는 형식은 오류 | ✅ |
| P4-A2 | 새 형식은 `register_area(scheme, factory)`로 등록만 하면 붙는다(예: 클라우드 저장소). 플랫폼 코드는 고치지 않는다 | ✅ |
| P4-A3 | **URL 공개 영역**은 읽기 전용이다. 주소가 `.md` 문서 하나면 그 문서를, 아니면 목록(`index.json`: 문서 이름과 주소)을 읽어 문서들을 가져온다. 인증 토큰(설정값)이 있으면 함께 보낸다. 가져온 내용은 설정된 초만큼 캐시한다 | ✅ |
| P4-A4 | URL 공개 영역의 경험 노트와 소유자 전용 메모는 **로컬 노트 폴더**(설정값)에 쓴다. 원격 원본은 고치지 않는다. 문서 목록에는 원격 문서와 로컬 노트가 함께 보인다 | ✅ |
| P4-A5 | 공개 영역에 `refresh()`가 있다. 로컬 폴더는 할 일이 없고, URL은 다시 가져온다. peer는 프로필을 만들기 전에 `refresh()`를 부른다. 원격을 못 가져오면 마지막 캐시를 쓰고 로그에 남긴다 | ✅ |

## 4-B. 공지 없는 P2P 직접 요청

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P4-B1 | **직접 요청**은 공지와 같은 모양의 서명된 문서다(`notice_id` 대신 `request_id`, `issuer_pub`, `until`, 선택 `audience`, 그 밖은 앱이 정함). 발행자가 서명한다 | ✅ |
| P4-B2 | `Peer.solicit(targets, request)`가 요청에 서명해 대상 peer들에게 A2A로 동시에 보내고 대상별 수신 확인을 돌려준다. 못 닿은 대상은 오류로 표시하고 나머지는 계속한다 | ✅ |
| P4-B3 | 플랫폼 op `solicit`: 받은 peer는 서명·만기를 확인하고, `audience`가 있으면 **broker와 같은 규칙**으로 자기 라벨과 맞춰 보고, 같은 `request_id`는 한 번만 받는다. 받은 요청은 받은 편지함(크기는 설정값)에 쌓고 바로 수신 확인을 돌려준다 | ✅ |
| P4-B4 | 받은 요청은 앱의 `on_request(peer, request, sender)`에 **뒤에서** 넘긴다(응답이 오래 걸려도 보낸 쪽은 기다리지 않는다). 받을 앱이 없으면 받은 편지함에만 남는다 | ✅ |

## 4-C. 원장 실적 조회

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P4-C1 | recorder API `GET /track/{pub}`: 그 공개키의 실적 집계(낸 것, 받은 사람 수, 받은·남긴 판정 수, 역할별 계약 수, 이벤트 수, 결재 수)만 준다. 상대방·내용·해시는 주지 않는다. 공개 여부는 설정값(끄면 404) | ✅ |
| P4-C2 | `track_of(peer, pub, recorder_urls)`가 여러 기록자의 집계를 합친다(못 닿은 기록자는 건너뛰고 표시) | ✅ |
| P4-C3 | `meets(track, need)`가 요구 실적(예: 역할 `review` 1회 이상, 결재 1회 이상)을 기계적으로 비교해 통과 여부와 모자란 항목을 돌려준다 | ✅ |
| P4-C4 | peer는 자기가 쓴 기록자 주소를 기억한다(`known_recorders`). 설정으로 더 줄 수 있다 | ✅ |

## 4-D. 역량 라벨 자율 갱신

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P4-D1 | 라벨은 두 가지다. **사람이 정한 라벨**(peer 설정, 예: 소속)과 **역량 라벨**(에이전트가 붙임). 프로필의 `labels`는 둘을 합친 것이고, `capabilities`에 역량 라벨마다 근거를 싣는다 | ✅ |
| P4-D2 | **원장 근거**: 실적 집계에서 역할별 계약 수가 문턱(설정값) 이상이면 `역할:<역할>` 라벨을 붙인다. 근거는 기록자와 횟수 | ✅ |
| P4-D3 | **지식 근거**: 비서가 LLM으로 공개 영역(소유자 전용 제외)에서 분야 라벨 후보와 근거 문장을 뽑는다. 근거 문장이 공개 영역에 **실제로 있을 때만** `분야:<분야>`를 붙인다. 분야 이름은 공개 영역의 말로 짓는다(번역하지 않음). 개수 상한은 설정값 | ✅ |
| P4-D4 | 라벨은 프로필을 게시할 때마다 다시 계산한다. 근거가 사라지면 라벨도 빠진다. 만기는 프로필 만기와 같다. LLM이 실패하면 지식 라벨 없이 원장 라벨만 붙인다 | ✅ |
| P4-D5 | 사람이 정한 라벨과 같은 이름의 역량 라벨은 따로 붙이지 않는다. 접두사(`역할:`, `분야:`)는 설정값 | ✅ |

## 4-E. 테스트

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P4-E1 | 단위 테스트(가짜 HTTP, 정해진 답의 LLM, 메모리 recorder) | ✅ |
| P4-E2 | **경연 모티브, 수집 방식**: 공지 없이 진행자가 검색으로 후보를 찾고, 심사자 후보의 실적을 미리 확인한 뒤 계약하고, 응모 후보들에게 직접 요청을 보내 응모를 받는다(테스트 안에서만) | ✅ |
| P4-E3 | **실제 LLM**: 공개 영역에서 근거 있는 분야 라벨만 붙는지, 실제 프로세스 recorder의 실적 조회가 되는지 확인 | ✅ |
| P4-E4 | 결과를 `dev/phase4/test-results.md`에 적는다 | ✅ |

## 범위 밖
