## 2. 기능별 확인

| 기능 | 확인한 것 |
|---|---|
| 공개 영역 주소 연결 | 경로·`file://`은 로컬 폴더, `http(s)://`는 URL 공개 영역. 새 형식(`s3://` 예)은 등록만으로 붙음. URL은 `index.json` 목록이나 문서 하나를 읽고, 토큰을 붙이고, 캐시하고, 못 가져오면 마지막 사본을 씀. 경험 노트와 소유자 메모는 로컬 노트 폴더에 씀 |
| 직접 요청 | 서명해 여러 peer에 동시에 보냄. 받는 쪽은 서명·만기·응모 대상 라벨·중복을 확인하고 받은 편지함에 쌓은 뒤 바로 수신 확인. 앱 처리는 뒤에서 하므로 보낸 쪽이 기다리지 않음(0.05초 지연 앱으로 확인). 받은 편지함 크기 제한 |
| 실적 조회 | `GET /track/{pub}`가 개수만 줌(상대방·해시 없음), 설정으로 끌 수 있음. 여러 기록자 합산과 실패 표시. `meets`가 모자란 항목을 "roles.review 0/1"처럼 알려 줌 |
| 역량 라벨 | 원장의 역할 계약 수가 문턱 이상이면 `역할:<역할>`, LLM이 고른 분야는 근거 문장이 공개 영역에 그대로 있을 때만 `분야:<분야>`. 근거 없는 "우주 항공"은 빠짐. LLM 실패 시 원장 라벨만. 사람이 정한 라벨과 겹치면 다시 안 붙임 |

## 3. 경연 모티브, 수집 방식 (공지 없음)

1. 진행자가 고급 검색 peer에 심사자 후보를 물었다. 닫힌 심사 그룹 회원이라 두 후보가 나왔다.
2. recorder 실적을 보니 한 명은 이전 이벤트에서 심사 계약 1회, 한 명은 0회였다. `meets`로 경험 있는 후보만 통과했다.
3. 그 후보로 역할 계약을 맺고, 사장님 결재를 받아 이벤트를 선언했다. 공지는 올리지 않았다(broker 공지 0건).
4. 고급 검색 peer로 주제에 맞는 응모 후보 2명을 골랐다. 관련 적은 1명과 협력사 1명은 고르지 않았다.
5. 고른 2명에게만 직접 요청을 보냈다. 각자의 대역 앱이 결재·계약을 확인하고 응모했다. 고르지 않은 사람의 받은 편지함은 비어 있었다.
6. 실적을 확인한 심사자가 심사하고 1건을 채택했다. 감사는 정상이었다.

## 4. 실제 LLM: 역량 라벨

| 공개 영역 | 붙은 분야 라벨 (근거는 모두 공개 영역 원문) |
|---|---|
| 클라우드 비용 최적화 5년, FinOps로 30% 절감, 쿠버네티스 운영·장애 대응 | 클라우드 비용 최적화, FinOps, 쿠버네티스 클러스터 운영 (+ 한 번은 장애 대응) |
| 대표이사, 회사 전략과 인재 육성 | 1회 "회사 전략과 인재 육성", 2회 "전략"·"인재 육성", 3회 "전략·인재육성" |

소유자 전용 문서("보안 등급 문서")는 근거로 쓰이지 않았다.

**발견하고 고친 것**: 처음 실행에서 사장님 peer의 분야 이름이 "Corporate Strategy", "Talent Development"처럼 영어로 나왔다. 근거 문장은 한국어 원문이었다. "분야 이름은 공개 영역의 말로, 번역하지 말 것"을 지시에 넣었고, 이후 세 번 모두 한국어였다(라벨 언어를 검사하는 실제 LLM 테스트 추가).

**확인된 한계**: 같은 공개 영역이라도 실행마다 분야를 나누는 단위가 달랐다(위 표). broker의 라벨 거르기는 글자가 같아야 맞으므로, **역량 분야 라벨로 정확히 거르는 것은 아직 믿을 수 없다.** 지금은 고급 검색 peer의 뜻 검색으로 찾는 것이 맞다. 대응(분야 표준 목록, 또는 라벨도 뜻으로 맞추기)은 5단계 검증에서 정한다. 역할 라벨(`역할:<역할>`)은 원장 숫자에서 나오므로 흔들리지 않는다.

## 5. 남은 한계

- URL 공개 영역은 읽기 전용이다. 클라우드 저장소는 등록 방식만 있고 구현은 없다.
- 직접 요청을 받을지는 라벨·서명·만기로만 기계적으로 정한다. 받은 뒤 응할지는 앱의 몫이다.
- 실적 조회는 공개키별 개수라 여러 키로 실적을 쪼개거나 부풀리는 일은 막지 못한다.
