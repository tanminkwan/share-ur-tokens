# 3단계 요구사항: 기본 서빙 peer

> 상태 표기: ⬜ 미착수 · 🟡 진행 · ✅ 테스트 통과(2026-10-30, [test-results.md](test-results.md)). 번호는 테스트 이름과 맞춘다(P3-A1 → `test_p3a1_...`).

## 0. 목표

broker는 AI 없이 기계적으로 일한다. 무거운 계산이나 넓은 시야가 필요한 일은 **역할을 맡은 peer**가 한다. 이 단계에서는 플랫폼이 기본으로 띄워 주는 인프라 peer 두 가지를 만든다(사용자 2026-10-30).

1. **고급 검색 peer**: broker의 프로필과 공지(이벤트)를 임베딩 벡터로 바꿔 두고, 뜻이 가까운 것을 벡터 거리로 찾아 준다. BM25로는 안 잡히는 "다른 말, 같은 뜻"을 찾는다.
2. **관전용 god peer**: 기록자의 열람 허용 목록에 있는 키로 원장 전체를 읽어 스스로 감사하고, 통계와 peer별 강점·실적을 낸다.

둘 다 범용이다. 특정 앱의 판정·역할 이름을 모른다. 둘 다 `python -m`으로 단독 실행되는 peer이고, 다른 peer는 A2A로 부른다. 임베딩 모델은 사용자가 운영하는 bge-m3 서비스(`POST /embed`, 1024차원)를 쓴다.

## 3-A. 공통 부품

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P3-A1 | **임베딩 인터페이스**(`Embedder`): 글 목록을 벡터 목록으로. 구현 `HttpEmbedder`는 bge-m3 서비스를 부르고, 설정된 크기로 나눠 보내고, 실패하면 설정 횟수만큼 다시 묻고, 개수가 안 맞거나 차원이 다르면 오류(`EmbedError`). 주소·나눔 크기·제한 시간·재시도는 설정값 | ✅ |
| P3-A2 | **벡터 색인**(`VectorIndex`, 구현 `MemoryVectorIndex`): 키별로 벡터와 부가 정보를 넣고 빼고, 질의 벡터와 코사인 유사도가 높은 순으로 상위 k개를 준다. 거르기 함수를 받을 수 있다. 넣을 때 정규화한다 | ✅ |
| P3-A3 | **서명 메시지**: A2A 메시지에 서명자·시각·서명을 붙이고 확인하는 함수. 서명 대상은 `{"op", "ts"}`, 시각 폭은 기존 설정값(`ARENA_SIG_WINDOW_SEC`) | ✅ |
| P3-A4 | **사람 없는 peer용 부품**: `NoOwner`(소유자에게 묻는 일은 모두 거절), `NoLLM`(항상 `LLMError`, 프로필은 공개 영역 첫 줄로 대신). 자율 peer는 LLM 없이도 뜬다 | ✅ |

## 3-B. 고급 검색 peer (`arena/peer/search_role.py`, `python -m arena.peers.search`)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P3-B1 | 역할 `search`를 공개한다. 설정된 broker 그룹마다 프로필과 (자기가 볼 수 있는) 공지를 가져와 색인한다. 색인 글은 프로필이면 요약·공개 역할·라벨, 공지면 제목·내용·종류 | ✅ |
| P3-B2 | **바뀐 것만 다시 임베딩**한다. 프로필은 버전, 공지는 내용 해시로 비교한다. broker에서 사라진(만기·마감) 항목은 색인에서 뺀다. 갱신 주기는 설정값 | ✅ |
| P3-B3 | op `search_profiles`: 질의 글과 선택 조건(그룹, 공개 역할, 라벨, 제외 공개키, k)을 받아 유사도 순으로 프로필 전체와 점수·그룹을 돌려준다. 검색 peer 자신은 결과에서 뺀다(broker에서 역할로 찾음). 최소 점수와 k 상한은 설정값 | ✅ |
| P3-B4 | op `search_notices`: 서명된 요청만 받는다. **broker와 같은 응모 대상 규칙**으로, 묻는 peer의 프로필 라벨에 맞는 공지만 돌려준다(검색 peer가 더 넓게 봐도 묻는 peer가 못 보는 공지는 안 준다) | ✅ |
| P3-B5 | **닫힌 그룹**의 프로필·공지는 그 그룹에 프로필이 있는 peer가 서명해서 물을 때만 준다. 열린 그룹은 누구나 | ✅ |
| P3-B6 | op `search_status`: 그룹별 색인 건수, 마지막 갱신 시각, 임베딩 모델 차원 | ✅ |
| P3-B7 | 임베딩 서비스가 멈추면 색인은 그대로 두고 갱신만 미루며, 로그에 남긴다. 질의 임베딩이 실패하면 오류를 돌려준다 | ✅ |

## 3-C. 관전용 god peer (`arena/peer/overseer_role.py`, `python -m arena.peers.overseer`)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P3-C1 | broker에서 역할 `record`로 기록자를 찾고(검색 결과의 recorder 주소), 자기 키로 원장 전체를 서명 요청으로 읽는다 | ✅ |
| P3-C2 | 읽은 사본을 **스스로 감사**한다(해시 체인, 참여자 서명, 기록자 서명). 기록자가 둘 이상이면 머리 해시를 서로 맞춰 본다. 처음 이상을 찾으면 로그에 경고를 한 번 남긴다 | ✅ |
| P3-C3 | **범용 통계**: 항목 수, 종류별 수, 서명자 수, 선언된 이벤트(종류, 결재자), 판정 이름별 수와 판정 페이로드의 숫자 항목 평균, 역할 이름별 계약 수, 공유 흐름 상위, 기간. 판정·역할 이름의 뜻은 모른다 | ✅ |
| P3-C4 | **peer별 강점·실적**: broker 프로필(요약 = 강점, 버전, 공개 역할, 라벨, 그룹)과 원장 기여 집계(낸 것, 받은 사람, 받은·남긴 판정, 역할, 이벤트, 결재)를 공개키로 묶는다 | ✅ |
| P3-C5 | 기록자의 접근 기록(허용·거부)을 함께 보인다 | ✅ |
| P3-C6 | op `overseer_snapshot`: 설정된 열람자 공개키가 서명해서 물을 때만 위 결과를 준다(관전 화면이 이 op를 부른다). 결과는 설정된 초만큼 캐시 | ✅ |
| P3-C7 | 쓰기·내용 열람·실명 확인 기능이 없다(그런 op가 없음을 테스트) | ✅ |

## 3-D. 단독 실행과 테스트

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P3-D1 | 두 peer 모두 설정(포트, 키 파일, 공개 영역 폴더, 라벨, broker 그룹 주소 목록)으로 단독 실행되고, 시작하면 프로필을 게시하고 주기 작업을 돈다 | ✅ |
| P3-D2 | 단위 테스트는 결정적 임베딩 대역(같은 글 → 같은 벡터, 단어가 겹치면 가까움)으로 돈다 | ✅ |
| P3-D3 | **실제 임베딩 테스트**: bge-m3 서비스로 "다른 말, 같은 뜻" 질의가 맞는 프로필·공지를 BM25보다 잘 찾는지 확인한다. 서비스가 없으면 이유를 밝히고 건너뛴다 | ✅ |
| P3-D4 | **실제 프로세스 테스트**: broker 프로세스, 검색 peer 프로세스, god peer 프로세스를 띄워 A2A로 질의한다 | ✅ |
| P3-D5 | 결과를 `dev/phase3/test-results.md`에 적는다 | ✅ |
