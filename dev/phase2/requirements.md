# 2단계 요구사항: 범용화와 peer 핵심

> 상태 표기: ⬜ 미착수 · 🟡 진행 · ✅ 테스트 통과(2026-10-30, [test-results.md](test-results.md)). 번호는 테스트 이름과 맞춘다(`test_p<번호>_...`, 예: P2-A3 → `test_pa3_...`).

## 0. 목표

에이전트 아레나는 **범용 플랫폼**이다. 개발 범위는 플랫폼(`arena/`)뿐이고, 아이디어 경연은 테스트 소재일 뿐이다(사용자 2026-10-30). 이 단계에서 할 일은 세 가지다.

1. **2-A 범용화**: 1단계 코드에 섞여 든 경연 전용 개념을 플랫폼에서 걷어 낸다. 앱마다 다른 규칙은 이벤트가 **선언**하고 플랫폼은 선언을 기계적으로 집행한다. 사장님 결재 같은 공동 서명도 범용 "이벤트 결재"로 넣는다.
2. **2-B peer 핵심**: 모든 peer가 가지는 범용 능력을 만든다. 신원, 공개 영역, 프로필 게시, A2A 통신, 역할 계약, 이벤트 결재, 앱 등록, LLM 어댑터, 기록자 역할.
3. **2-C 경연 모티브 통합 테스트**: 테스트 코드 안의 작은 대역 앱으로 경연 흐름(사장님 결재 → 이벤트 선언 → 역할 계약 → 공지 → 응모 → 심사 → 채택)을 플랫폼 API만으로 끝까지 재현한다. 앱(`apps/`)과 시연 장치(`demo/`)는 만들지 않는다. 기존 `app/`은 건드리지 않는다.

플랫폼(`arena/`)에는 앱 용어가 없고 테스트 밖의 어떤 앱도 import하지 않는다. 테스트가 이를 검사한다.

## 2-A. 범용화

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P2-A1 | 원장 항목의 이벤트 식별자는 `event_id`다. 플랫폼 코드에 `call_id`, `공모`, `idea`, `review`, `adopt` 같은 앱 용어가 없다(테스트가 소스를 검사) | ✅ |
| P2-A2 | 새 항목 종류 **이벤트 선언**(`event`). 발행자가 서명하며 `event_id`, `issuer`, `kind`, `policy`를 담는다. 같은 `event_id`는 한 번만 선언된다. policy 모양이 틀리면 거절 | ✅ |
| P2-A3 | **policy**는 네 가지를 선언한다. `roles`(이 이벤트에서 계약할 수 있는 역할), `conflict_roles`(이 역할로 계약한 사람은 이 이벤트에 publish 못 함), `verdict_roles`(이 판정은 이 역할 계약자만 남길 수 있음, 값 `issuer`는 이벤트 발행자), `hidden_roles`(공개 확인에서 계약자를 숨길 역할) | ✅ |
| P2-A4 | 역할 계약은 선언된 이벤트에만, 그 이벤트의 발행자만, policy의 `roles` 안에서 맺는다. 플랫폼 설정의 고정 역할 목록(`ARENA_CONTRACT_ROLES`)은 없앤다 | ✅ |
| P2-A5 | 범용 규칙(서명, 해시 체인, 시각 순서, 먼저 등록, 재전송 방지, 중복 판정, "받은 사람만 평가")은 이벤트가 없어도 항상 적용된다. 이벤트를 지정한 publish·feedback은 그 이벤트의 policy를 추가로 따른다. 선언되지 않은 이벤트를 가리키면 거절 | ✅ |
| P2-A6 | 기여 집계는 판정 이름을 모른다. 공개키별로 낸 내용 수, 받은 사람 수(자기 제외), 받은 판정 수(판정별), 남긴 판정 수(판정별), 맡은 역할 수(역할별), 선언한 이벤트 수 | ✅ |
| P2-A7 | recorder 공개 확인(`GET /entries/{hash}`)은 종류별 공개 항목만 준다. 계약이면 이벤트·역할·발행자, 그리고 그 역할이 policy의 `hidden_roles`에 없을 때만 계약자. 이벤트 선언이면 이벤트·발행자·종류 | ✅ |
| P2-A9 | **이벤트 결재**: 이벤트 선언은 결재자 목록(`approvers`)을 가질 수 있고, 그때는 발행자와 **결재자 전원의 서명**이 있어야 기록된다. 결재자는 발행자와 달라야 한다. 공개 확인은 이벤트 선언의 결재자 목록을 준다(결재 서명이 원장에 있으므로 누구나 확인할 수 있다) | ✅ |
| P2-A10 | broker 프로필 검색 결과는 프로필 전체(앱이 덧붙인 항목 포함, 예: 기록자의 recorder 주소)에 필명·점수·출처 broker를 더해 돌려준다 | ✅ |
| P2-A8 | broker 공지에서 플랫폼이 요구하는 필드는 `notice_id`, `issuer_pub`, `until`뿐이다(`audience`는 선택). 검색 대상 글은 `title`, `text`, `kind`가 있으면 쓰고 없으면 빈 글로 본다. 나머지 필드는 앱이 정하며 broker는 그대로 보관만 한다 | ✅ |

## 2-B. peer 핵심 (`arena/peer/`, `arena/llm.py`, `arena/a2a.py`)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P2-B1 | 설정의 읽기 방식은 기반 클래스(`EnvSettings`)로 떼어, 나중에 플랫폼 위의 앱도 같은 `.env` 방식으로 자기 설정을 선언할 수 있게 한다. 플랫폼 키는 `Settings`에 있고 `.env.example`이 모든 키를 담는다 | ✅ |
| P2-B2 | **LLM 어댑터**: OpenAI 호환(삼성SDS Cloud AI 서비스)과 Claude 두 백엔드를 `ARENA_LLM_BACKEND`로 고른다. JSON 스키마 출력을 요구하고, 빈 응답·JSON 아님·HTTP 오류는 설정 횟수만큼 다시 묻는다. 끝내 실패하면 `LLMError`. 동시 호출 상한, 제한 시간, 최대 토큰, 모델명은 설정값 | ✅ |
| P2-B3 | `reasoning_effort`를 받지 않는 엔드포인트면 한 번 빼고 다시 묻는다 | ✅ |
| P2-B4 | **공개 영역**(`PublicArea` 인터페이스, 구현은 `LocalFolderArea`): 폴더의 마크다운 문서를 읽고, 경험 노트를 덧붙인다. 이름이 `_`로 시작하는 문서(소유자 규칙, 상황)는 **소유자 전용**이라 프로필 요약과 남에게 주는 응답에 쓰지 않는다 | ✅ |
| P2-B15 | 공개 영역에 소유자 전용 문서로 메모를 남길 수 있다(예: 비서의 판단 기록). 이 메모는 프로필에 들어가지 않는다 | ✅ |
| P2-B16 | peer는 주소로 recorder 클라이언트를 만든다(주입 가능, 테스트는 메모리 recorder) | ✅ |
| P2-B5 | **프로필**: 비서가 공개 문서(소유자 전용 제외)를 LLM으로 요약해 서명 게시한다. 사람이 정한 것(공개 역할 `offers`, 라벨 `labels`)은 peer 설정에서 오고, 만기는 설정값, 다시 게시할 때마다 버전이 오른다. 앱이 프로필에 덧붙일 항목(예: recorder 주소)을 줄 수 있다 | ✅ |
| P2-B6 | **A2A**: 모든 peer는 Agent Card를 공개하는 A2A 1.0 서버다. 메시지는 JSON 한 개(`op` 필드로 구분). 등록된 op만 받고 모르는 op는 거절. 처리 중 예외는 `{ok:false, error}`로 돌려준다 | ✅ |
| P2-B7 | 전송은 `Transport` 인터페이스 뒤에 둔다. 실제는 A2A HTTP, 테스트는 같은 프로세스 안의 `LocalTransport` | ✅ |
| P2-B8 | **앱 등록**: peer는 앱 목록으로 조립된다. 앱은 op 처리기, 공개 역할, 프로필 덧붙임, 시작 시 돌릴 작업을 제공한다. 새 앱은 peer 코드를 고치지 않고 등록만으로 붙는다. 같은 op를 두 앱이 등록하면 조립 시 오류 | ✅ |
| P2-B9 | **역할 계약(engage)**: 플랫폼의 범용 op. 요청 역할이 내 `offers`에 없거나 계약서의 계약자가 내가 아니면 거절. 수락 여부의 판단은 그 역할을 맡은 앱이 정한다(없으면 거절). 수락하면 계약서에 서명해 돌려준다 | ✅ |
| P2-B10 | **기록자 역할**(플랫폼 인프라 역할 `record`): peer가 recorder 서비스를 품고 recorder API를 자기 포트로 연다. 프로필에 recorder 주소를 덧붙인다 | ✅ |
| P2-B11 | **영수증**: peer는 자기가 기록한 항목의 기록자 서명 응답을 보관하고, 그 서명이 기대한 기록자 키로 되어 있는지 검사할 수 있다 | ✅ |
| P2-B12 | **소유자 인터페이스**(`Owner`): peer 뒤의 사람. 비서가 묻고(예/아니오와 이유), 글을 받는다. 시연은 페르소나 구현, 나중에 사람 화면 구현이 같은 인터페이스를 쓴다 | ✅ |
| P2-B14 | **결재 요청(approve)**: 플랫폼의 범용 op. 이벤트 선언 페이로드를 받아, 내가 결재자 목록에 있고 결재를 맡은 앱이 승인하면 서명해 돌려준다. 결재를 맡은 앱이 없으면 거절 | ✅ |
| P2-B13 | **관측 로그**(`EventLog`): 모든 구성 요소는 주입받은 로그에 (종류, 행위자, 글)을 남긴다. 대시보드가 이것을 읽는다 | ✅ |

## 2-C. 경연 모티브 통합 테스트 (테스트 안에서만)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P2-C1 | 테스트 안의 대역 앱(결재, 역할 수락, 제출 받기)만 쓰고, 나머지는 모두 플랫폼 API로 경연 흐름을 끝까지 돈다 | ✅ |
| P2-C2 | **사장님 결재**: 진행자가 broker에서 결재자 라벨(`직책:대표이사`)로 사장님 peer를 찾아 결재를 요청하고, 결재 서명이 붙은 이벤트 선언이 원장에 기록된다. 결재가 반려되면 이벤트는 기록되지 않는다 | ✅ |
| P2-C3 | 기록자는 응모 그룹 broker에서 역할(`record`)로, 심사자는 닫힌 심사 그룹 broker에서 역할(`review`)로 찾아 계약한다. 공지에는 이벤트 해시, 결재자, 기록자, 계약 해시가 실리고 심사자는 실리지 않는다 | ✅ |
| P2-C4 | 응모자는 라벨로 공지를 보고, recorder 공개 확인으로 결재와 계약을 확인하고, broker 프로필로 결재자 라벨을 확인한 뒤 먼저 등록 → 제출(p2p) → 공유를 기록하고 기록자 서명 영수증을 보관한다 | ✅ |
| P2-C5 | policy가 집행된다. 계약 없는 심사 판정 거절, 발행자 아닌 채택 거절, 계약된 기록자·심사자의 응모 거절 | ✅ |
| P2-C6 | 기여 집계에 사장님의 결재 1건, 심사자의 역할·판정, 응모자의 받은 판정이 나온다. 감사가 정상이고 과거 항목을 고치면 탐지된다. 허용 목록 밖의 전체 열람은 거부된다 | ✅ |
| P2-C7 | 같은 흐름을 **실제 프로세스와 실제 LLM**으로도 돈다. broker는 `python -m arena.broker` 별도 프로세스, peer는 A2A 서버, 기록자 peer는 recorder API를 열고, 프로필 요약·역할 수락·결재 판단은 삼성SDS Cloud AI 서비스가 한다 | ✅ |

## 2-E. 테스트

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P2-E1 | 단위 테스트는 네트워크·LLM 없이 돈다. LLM은 정해진 답을 돌려주는 테스트 대역으로 바꾼다(판단 로직을 같은 입력에서 같은 결과로 검사하기 위함) | ✅ |
| P2-E2 | **실제 LLM 테스트**: 삼성SDS Cloud AI 서비스 키로 LLM 어댑터, 프로필 요약, 시연 전체 흐름(끝까지 실행, 아이디어 1건 이상, 채택 1건 이상, 감사 정상, 변조 탐지)을 돈다. 키가 없으면 이유를 밝히고 건너뛴다. 오프라인 템플릿으로 대체하지 않는다 | ✅ |
| P2-E3 | 결과를 `dev/phase2/test-results.md`에 적고 실제 LLM 실행 기록을 첨부한다 | ✅ |
