# 1단계 요구사항: 인프라 서비스 (broker · collector)

> 상태 표기: ⬜ 미착수 · 🟡 진행 · ✅ 테스트 통과(2026-10-30, [test-results.md](test-results.md)). 번호는 테스트 이름과 맞춘다(`tests/test_<모듈>.py::test_r<번호>_...`).

## 0. 목표와 범위

플랫폼의 **AI 없는 인프라 두 가지**를 독립 서비스로 만든다. 둘 다 HTTP JSON API로 동작하는 별도 프로세스이며, 구성원 peer가 자기 프로세스 안에 품고 돌릴 수도 있다(라이브러리 + 서버 포장의 두 겹).

- **broker**: 프로필·공지 게시판, 검색, 닫힌 그룹 허가, 이웃 broker와 공지 공유
- **collector**: 서명된 해시 체인 원장. 기록·검증·감사·열람 통제·파일 영속화. **원장 보관소는 하나**다(기록자 여럿의 분산·합의는 마지막 단계, 사용자 2026-10-30)

범위 밖(2단계 이후): peer 노드, A2A 통신, LLM, 공개 영역, 앱 계층. 기존 `app/`은 이번 단계에서 건드리지 않는다(다음 단계에서 새 서비스로 옮긴다).

## 1. 공통

| 번호 | 요구사항 | 상태 |
|---|---|---|
| R1-1 | 모든 설정값은 `.env`에서 읽는다. 코드에 포트·주소·초 단위 만기·상한·경로 상수를 직접 쓰지 않는다. `.env.example`에 모든 키와 기본값·설명을 둔다 | ✅ |
| R1-2 | 설정은 `arena.config.Settings` 하나로 읽고, 필수 키가 없으면 어느 키가 없는지 말하는 오류로 멈춘다. 테스트는 환경변수로 설정을 덮어쓸 수 있다 | ✅ |
| R1-3 | 신원은 ed25519 키다. 생성, 파일 저장·불러오기(서비스 재시작 뒤에도 같은 키), 서명, 검증, 표시용 **필명**(`필명-` + 공개키 앞 6자) | ✅ |
| R1-4 | 정규화 직렬화(`canon`)와 SHA-256 해시(`h`)는 키 순서·공백에 관계없이 같은 내용이면 같은 값 | ✅ |
| R1-5 | **서명 요청 형식**: 서명이 필요한 API 호출은 헤더 `X-Arena-Pub`, `X-Arena-Ts`, `X-Arena-Sig`를 붙인다. 서명 대상은 `{"op": "<METHOD> <PATH>", "ts": <ts>}`. 시각 차가 설정값(`ARENA_SIG_WINDOW_SEC`)을 넘으면 거절 | ✅ |
| R1-6 | 검색기는 BM25(단어 + 두 글자 조각)이고 `Searcher` 인터페이스 뒤에 있어 임베딩 검색기로 바꿀 수 있다. 한국어 질의가 형태소 분석 없이 관련 문서를 상위에 올린다 | ✅ |

## 2. 원장 라이브러리 (`arena/ledger.py`)

기존 `app/ledger.py`의 규칙을 그대로 옮기고 테스트로 못 박는다.

| 번호 | 요구사항 | 상태 |
|---|---|---|
| R2-1 | 항목 종류는 `contract`, `publish`, `share`, `feedback` 네 가지. 다른 종류는 거절 | ✅ |
| R2-2 | 참여자 서명: publish=작성자, share=제공자+수령자, feedback=평가자, contract=발행자+계약자. 하나라도 없거나 틀리면 거절 | ✅ |
| R2-3 | 해시 체인: 각 항목은 이전 해시를 담고, 기록자가 항목 해시에 서명(기록자 서명)한다 | ✅ |
| R2-4 | 시각: 이전 항목보다 앞서면 거절 (기록자가 하나이므로 시각은 기록자 시계가 정한다) | ✅ |
| R2-5 | 먼저 등록: 같은 내용 해시의 두 번째 publish는 거절 | ✅ |
| R2-6 | 역할 충돌: 같은 이벤트의 계약자(기록자·심사자)는 그 이벤트에 publish 못 함 | ✅ |
| R2-7 | share·feedback은 publish된 내용에만. share·contract의 nonce 재사용은 거절 | ✅ |
| R2-8 | contract의 역할은 설정된 허용 목록(`ARENA_CONTRACT_ROLES`)에 있어야 한다 | ✅ |
| R2-9 | feedback: 같은 평가자·같은 내용·같은 판정은 한 번. `review` 판정은 그 이벤트의 계약자만. 평가자는 그 내용을 share로 받은 적이 있어야 한다 | ✅ |
| R2-10 | 감사(`audit_chain`): 해시 체인, 참여자 서명, 기록자 서명을 다시 검증해 첫 변조 위치를 알려 준다 | ✅ |
| R2-11 | 기여 집계(`contribution`): 필명별 받은 사람 수(자기 수령 제외), 채택 수, 맡은 역할 수 | ✅ |
| R2-12 | **파일 영속화**: 항목을 추가할 때마다 한 줄씩 덧붙이는 파일(JSONL)에 쓰고, 시작할 때 읽어 감사한 뒤 이어 쓴다. 파일이 변조되어 있으면 시작을 거부한다. 경로는 설정값 | ✅ |

## 3. collector 서비스 (`arena/collector/`)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| R3-1 | `POST /entries`: 종류·페이로드·참여자 서명을 받아 원장 규칙을 통과하면 기록하고 `seq`, `hash`, 기록자 서명(`seal`)을 돌려준다. 거절 시 이유를 돌려준다. 동시 요청은 직렬화한다 | ✅ |
| R3-2 | `GET /entries/{hash}`: 누구나. 그 해시의 항목이 있는지, 기록자 서명이 맞는지, 종류, 그리고 contract일 때 역할·이벤트·발행자(계약자는 역할이 `record`일 때만)를 돌려준다. 다른 내용은 돌려주지 않는다 | ✅ |
| R3-3 | `GET /audit`: 누구나. 감사 결과, 길이, 머리 해시 | ✅ |
| R3-4 | `GET /chain`: 열람 허용 목록에 있는 공개키가 서명 요청(R1-5)으로 부를 때만 전체 체인을 준다. 허용·거부 모두 접근 기록에 남기고, 접근 기록은 설정된 크기만 유지한다 | ✅ |
| R3-5 | `GET /access-log`: 열람 허용 목록의 서명 요청만. 최근 접근 기록 | ✅ |
| R3-6 | `GET /health`: 이름, 필명(공개키), 길이, 머리 해시 | ✅ |
| R3-7 | 열람 허용 목록은 설정(`ARENA_COLLECTOR_READERS`)으로 준다. 비어 있으면 아무도 전체 열람 못 함 | ✅ |
| R3-8 | `python -m arena.collector`로 단독 실행된다. 키 파일·원장 파일·포트는 설정값. 재시작하면 같은 키와 같은 체인으로 이어진다 | ✅ |
| R3-9 | `CollectorClient`(httpx)는 위 API를 메서드로 감싸고, 테스트용 `InMemoryCollectorClient`는 네트워크 없이 서비스 객체를 직접 부른다. 둘은 같은 인터페이스(`CollectorAPI`) | ✅ |

## 4. broker 서비스 (`arena/broker/`)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| R4-1 | `POST /profiles`: 서명된 프로필(주소 `url`, 요약, 공개 역할 `offers`, 라벨 `labels`, 만기 `until`, 버전 `ver`)을 게시·갱신한다. 주소도 서명 대상에 들어간다. 서명이 틀리면 거절 | ✅ |
| R4-2 | 프로필·공지는 만기가 지나면 목록·검색·열람에서 사라진다 | ✅ |
| R4-3 | `GET /profiles`: 활성 프로필 목록. 이웃 broker에도 물어 합친다(이웃이 멈춰도 나머지는 답한다) | ✅ |
| R4-4 | `GET /profiles/search?q=&role=&label=&exclude=&k=`: BM25 검색. 역할·라벨로 좁힐 수 있고, 이웃에 물어 점수순으로 합쳐 상위 k | ✅ |
| R4-5 | `POST /notices`: 서명된 공지(종류, 제목, 내용, 응모 대상 라벨 `audience`, 조건, 마감 `until`, 발행자 공개키·주소, 기록자, 계약 해시 목록) 게시. 이웃 broker에 한 번 전달하고, 받는 broker는 서명을 다시 확인한다 | ✅ |
| R4-6 | `POST /notices/{id}/close`: 발행자 서명으로만 마감. 이웃에 전달 | ✅ |
| R4-7 | `GET /notices`: 서명 요청(R1-5)이고 이 broker에 프로필이 있는 peer만. **응모 대상 라벨이 모두 그 peer의 프로필 라벨에 있는 공지**만 보인다 | ✅ |
| R4-8 | `GET /notices/search?q=&k=`: R4-7의 보이는 공지 안에서 BM25 | ✅ |
| R4-9 | **닫힌 그룹**: 소유자 공개키가 설정되면, 소유자가 서명한 기간 있는 허가(`POST /grants`)를 받은 공개키만 프로필 게시·목록·검색을 할 수 있다. 허가는 만기로 끝난다(회수 없음) | ✅ |
| R4-10 | `GET /health`: 이름, 공개키, 프로필 수, 공지 수, 이웃 목록 | ✅ |
| R4-11 | `python -m arena.broker`로 단독 실행. 포트·이웃 주소·소유자 공개키·키 파일은 설정값 | ✅ |
| R4-12 | `BrokerClient`(httpx)와 `InMemoryBrokerClient`는 같은 인터페이스(`BrokerAPI`) | ✅ |

## 7. 이번 단계에서 LLM을 쓰지 않는 이유

broker와 collector는 설계상 AI가 없다(판단은 peer가 한다). 그래서 1단계 테스트에는 LLM 호출이 없다. 삼성SDS Cloud AI 서비스 키는 2단계(peer·LLM 어댑터)부터 테스트에 쓴다.
