# 5단계 요구사항: 검증과 플랫폼 완성

> 상태 표기: ⬜ 미착수 · 🟡 진행 · ✅ 테스트 통과. 번호는 테스트 이름과 맞춘다(P5-A1 → `test_p5a1_...`).

## 0. 목표

이 단계를 통과하면 **플랫폼 완성**이다. 세 부분으로 나눈다.

1. **5-A 인수에 필요한 범용 기능**: 이벤트 종료, 공동 확인(여러 당사자 서명), 역량 분야 표준 목록.
2. **5-B 검증**: 변조와 권한 없는 열람을 한곳에 모아 점검하고, 실제 LLM 흐름을 반복해 안정성을 잰다.
3. **5-C 인수 확인**: peer 간 가위바위보 이벤트([../acceptance-rps.md](../acceptance-rps.md))를 메모리 세계와 실제 프로세스·실제 LLM으로 돈다.

## 5-A. 범용 기능

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P5-A1 | **이벤트 종료**(`close`): 발행자가 서명하는 원장 항목. 결과 해시(`result_hash`)를 담을 수 있다. 선언된 이벤트만, 발행자만, 한 번만 닫는다 | ⬜ |
| P5-A2 | 종료된 이벤트를 가리키는 계약·먼저 등록·판정·공동 확인은 거절한다("event closed") | ⬜ |
| P5-A3 | **공동 확인**(`attest`): 종류(`kind`), 대상(`subject`), 값(`value`), 당사자 목록(`parties`), nonce를 담고, 당사자 **전원**이 서명해야 기록된다. 당사자는 한 명 이상이고 겹치지 않는다 | ⬜ |
| P5-A4 | 같은 이벤트 안에서 같은 (종류, 대상)은 한 번만 공동 확인된다. nonce는 한 번만 쓴다 | ⬜ |
| P5-A5 | 이벤트 policy에 `attest_roles`(종류 → 역할 또는 `issuer`)를 둘 수 있다. 정해진 종류는 당사자 전원이 그 역할의 계약자여야 한다(`issuer`면 당사자가 발행자 한 명). 정하지 않은 종류는 자유 | ⬜ |
| P5-A6 | 기여 집계에 공동 확인 종류별 참여 수(`attested`)와 닫은 이벤트 수(`closed`)를 더한다. 통계에 닫힌 이벤트와 공동 확인 종류별 수를 더한다 | ⬜ |
| P5-A7 | recorder 공개 확인은 종료면 이벤트·발행자·결과 해시, 공동 확인이면 종류·대상·당사자·값, 먼저 등록이면 작성자·내용 해시를 준다(내용은 원장에 없으므로 해시까지만) | ⬜ |
| P5-A8 | **역량 분야 표준 목록**(`ARENA_LABEL_FIELD_VOCAB`, 쉼표 목록): 비어 있지 않으면 분야 라벨은 목록 안의 이름만 붙는다(LLM에 목록을 주고, 목록 밖 이름은 버림). 비어 있으면 자유롭게 짓는다(4단계 동작) | ⬜ |

### broker 그룹 식별자 (사용자 2026-10-30: 어떤 그룹에서 일어난 일인지 추적)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P5-A9 | broker는 그룹 식별자(`ARENA_BROKER_GROUP_ID`)를 가진다. 같은 그룹의 broker는 같은 식별자를 쓴다. `GET /health`, 프로필 목록·검색 결과에 `group_id`가 실린다 | ⬜ |
| P5-A10 | 공지는 발행자가 서명한 `group_id`를 담아야 하고, broker는 자기 그룹과 다른 공지를 받지 않는다(이웃이 전달한 공지도 같음) | ⬜ |
| P5-A11 | **원장의 모든 항목**은 페이로드에 `group_id`(빈 값 아님)를 담는다. 없으면 기록자가 거절한다. 당사자가 함께 서명하므로 나중에 바꿀 수 없다 | ⬜ |
| P5-A14 | **그룹 생성 공증**(사용자 2026-10-30): broker 그룹을 처음 만드는 peer가 **그룹 선언**(`group`) 항목을 남긴다. 만든 peer가 서명하고 `group_id`, 만든 peer(`founder`), 닫힌 그룹 여부(`closed`), 소속 broker 공개키 목록(`brokers`)을 담는다. 같은 `group_id`는 한 번만 선언된다 | ⬜ |
| P5-A15 | 그룹 선언을 요구하는 설정(`ARENA_RECORDER_REQUIRE_GROUP`, 기본 켬)이 켜져 있으면, 그룹 선언 밖의 모든 항목은 **이미 선언된 그룹**의 `group_id`만 쓸 수 있다(아니면 "unknown group"). 그래서 모든 기록이 그룹을 만든 peer까지 이어진다 | ⬜ |
| P5-A17 | **만민 그룹**(사용자 2026-10-30: 태초부터 존재하는 만민을 위한 broker 그룹): 제네시스가 만드는 열린 그룹(`ARENA_GENESIS_GROUP_ID`, 기본 `public`). 그룹 선언으로 만들 수 없고(이미 있음), 닫힌 그룹이 될 수 없다(소유자 설정 시 시작 오류). 그룹 식별자를 정하지 않은 broker는 만민 그룹이다 | ⬜ |
| P5-A18 | **제네시스**(사용자 2026-10-30: god이 broker와 recorder를 만들면서 생태계가 시작되고, 그 최초의 행위를 제네시스라 부른다): god peer가 만민 그룹 broker와 기록자를 만들고, 원장의 **0번 항목으로 제네시스**(`genesis`)를 남긴다. god이 서명하고 만민 그룹 식별자, god, broker, recorder의 공개키를 담는다. 제네시스는 원장 맨 앞에 한 번만 온다. 그룹 선언 요구가 켜져 있으면 원장은 제네시스로 시작해야 하고, 만민 그룹은 제네시스 뒤부터 선언 없이 쓰인다. god의 키는 처음부터 그 기록자의 열람 허용 목록에 있다. `python -m arena.genesis`가 이 행위를 하고, 키와 원장은 파일에 남아 다시 띄우면 같은 생태계로 이어진다(저장된 제네시스와 키가 다르면 시작 거부) | ⬜ |
| P5-A19 | **이벤트 규칙의 공증**(사용자 2026-10-30: 경기 방식을 알려야 peer의 AI 에이전트끼리 논란 없이 일관되게 진행): 이벤트 선언과 역할 계약은 규칙 문서의 해시(`rules_hash`)를 담을 수 있고, 공개 확인이 그 값을 돌려준다. 규칙 글은 공지에 자연어로 싣고, 계약에 서명하는 것은 그 규칙에 동의한다는 뜻이다 | ⬜ |
| P5-A16 | 공개 확인은 그룹 선언이면 `group_id`, `founder`, `closed`, `brokers`를 준다. 기여 집계에 만든 그룹 수(`groups`), 관전 통계에 선언된 그룹 목록을 더한다 | ⬜ |
| P5-A12 | 공개 확인 응답에 `group_id`, 관전 통계에 그룹별 항목 수가 실린다 | ⬜ |
| P5-A13 | peer는 broker 그룹의 식별자를 `group_id(그룹 이름)`로 얻는다(broker에 물어 기억) | ⬜ |

## 5-D. 플러그인 구조와 SOLID 정리 (사용자 2026-10-30: peer 앱이 탑재되는 방식은 제대로 주입되게 플러그인·인터페이스 설계를 해야 한다. 필요하면 앱 개발 규약집을 만든다)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P5-D1 | **앱 문맥 주입**: 앱은 peer 객체가 아니라 앱 문맥(`AppContext`)만 받는다. 문맥은 공개키·필명·주소·서명, 설정·시계·로그, LLM·소유자·공개 영역, broker 그룹·recorder 클라이언트, 통신(`call`, `solicit`), 그룹 식별자, 영수증, 프로필 다시 게시, **앱 전용 저장소**만 준다 | ⬜ |
| P5-D2 | **작은 능력 인터페이스**: `OpProvider`(op), `OfferProvider`(공개 역할), `RoleAcceptor`(역할 수락), `EventApprover`(결재), `RequestReceiver`(직접 요청 받기), `ProfileContributor`(프로필 덧붙임), `Lifecycle`(시작·멈춤). 앱은 필요한 것만 구현하고, peer는 구현한 능력만 연결한다 | ⬜ |
| P5-D3 | **op 처리 함수**는 `(문맥, 메시지, 머리)`를 받는다. 머리(`MessageHead`)는 그룹·이벤트·대화 식별자다. peer 인스턴스에 머리를 넣어 두는 숨은 통로를 없앤다 | ⬜ |
| P5-D4 | **플랫폼 op도 내장 앱**: 역할 계약(engage), 결재(approve), 직접 요청(solicit)은 같은 플러그인 방식의 내장 앱이다. 내장 op 이름은 예약되어 다른 앱이 덮어쓸 수 없다 | ⬜ |
| P5-D5 | **앱 등록 규칙**: 앱은 이름(`name`)과 버전(`version`)을 가진다. 이름 중복, op 중복, 예약 op 사용, 능력이 하나도 없는 앱은 조립 시 오류. 설정의 `모듈:팩토리` 목록으로 앱을 불러올 수 있다(`load_apps`) | ⬜ |
| P5-D6 | **기본 비서 분리**: 상태·저장, 도구, 에이전트 루프, 메시지 처리, 게시판 읽기를 나눈다. 도구는 `Tool`(이름, 설명, 인자 틀, 개최자 전용 여부, 실행)로 만들어 **등록**하며, 비서를 고치지 않고 도구를 더할 수 있다 | ⬜ |
| P5-D7 | **원장 항목 종류 등록**: 항목 종류마다 서명자, 고유 규칙, 공개 확인에 보일 항목, 기여 집계를 한 객체(`EntryType`)로 묶어 등록한다. 종류를 더할 때 원장·recorder·통계를 고치지 않는다 | ⬜ |
| P5-D8 | **broker 인터페이스 분리**: `ProfileBoard`, `NoticeBoard`, `GroupAdmin`, `Health`로 나누고 `BrokerAPI`는 이들의 합이다. 각 사용처는 필요한 인터페이스에만 기댄다 | ⬜ |
| P5-D9 | **앱 개발 규약집**(`dev/app-guide.md`): 앱의 구조, 능력 인터페이스, 문맥으로 할 수 있는 것과 하면 안 되는 것, op·메시지 규칙(머리, 서명), 지속성, 설정, 테스트 방법, 등록 방법 | ⬜ |
| P5-D11 | **앱 SDK와 어댑터**(사용자 2026-10-30: 앱은 별도 개발자 생태계가 생길 것이니 인터페이스 SDK나 규약집을 만들 것. 플러그인용 adaptee도 필요): 외부 개발자가 기대는 공개 면 `arena.sdk`(인터페이스, 문맥 인터페이스, SDK 버전, 도구, 불러오기, 패키지 진입점 `arena.apps` 찾기, 테스트 하네스 `AppHarness`). 어댑터로 앱 인터페이스를 모르는 것을 앱으로 바꾼다: 함수 묶음(`function_app`), 기존 HTTP 서비스·기간계 시스템(`HttpServiceAdapter`), 아레나 peer가 아닌 A2A 에이전트(`A2AAgentAdapter`). 앱이 밝힌 SDK 주 버전이 다르면 조립 시 거절. 실행 중 설치(`Peer.install`) | ⬜ |
| P5-D10 | 동작은 바꾸지 않는다. 지금까지의 테스트가 모두 그대로 통과한다(앱 인터페이스가 바뀐 곳은 테스트를 새 인터페이스로 옮긴다) | ⬜ |

## 5-E. 이벤트의 앱 지정과 실행 방식 (사용자 2026-10-30: 이벤트를 게시할 때 쓸 앱과 실행 방식을 명시하고, 앱에는 유일성을 보장하는 id(uuid나 hash)를 탑재해 peer 에이전트가 식별할 수 있게 한다)

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P5-E1 | **앱 식별자**: 모든 앱은 `app_id`(UUID)를 가진다. 조립 시 UUID 형식과 peer 안에서의 유일성을 검사한다. 플랫폼 앱(내장 앱, 기본 비서, 기록자·검색·god)은 고정 UUID를 쓴다. 플랫폼은 앱 코드의 해시(`app_fingerprint`)를 계산해 같은 코드인지 확인할 수 있게 한다 | ⬜ |
| P5-E2 | **이벤트의 블록**(사용자 2026-10-30: event에도 app list 블럭이 나눠져 있어야 함): 이벤트 공지와 원장의 이벤트 선언은 실행 방식 블록 `mode`와 **앱 목록 블록** `apps` = `[{id, name, version, hash?, required?}, ...]`을 따로 담는다(규칙 글 `rules`, 역할 `policy`와도 별개). 원장은 두 블록의 모양을 검사하고(앱을 쓰는 방식이면 목록이 비면 안 됨), 공개 확인이 그 값을 돌려준다 | ⬜ |
| P5-E3 | **실행 방식**: `assistant`(앱 없이 기본 비서가 자연어 규칙으로, 원초적 방식), `app`(지정한 앱이 있어야 참여), `app_or_assistant`(앱이 있으면 앱, 없으면 기본 비서) | ⬜ |
| P5-E7 | **앱 확인은 코드로**(사용자 2026-10-30: LLM이 uuid를 읽고 토큰을 쓰지 않게): 앱 설치 여부·버전·코드 해시·원장 대조는 배정기 코드가 하고, 앱 식별자는 LLM 프롬프트에 넣지 않는다 | ⬜ |
| P5-E4 | **이벤트 배정기**(내장 앱 `platform.events`): 내가 속한 모든 broker 그룹의 변경분을 읽고, 원장의 이벤트 선언과 공지의 규칙 해시·앱 지정이 같은지 확인한 뒤, 실행 방식에 맞는 앱(`EventHandler` 능력)을 `app_id`로 찾아 넘긴다. 버전은 주 버전이 같고 지정 버전 이상, 지정 해시가 있으면 내 앱의 코드 해시와 같아야 한다. 맞는 앱이 없으면 넘기지 않고 이유를 남긴다. 읽은 위치는 재시작 뒤에도 이어진다 | ⬜ |
| P5-E5 | **이벤트 받기 능력**(`EventHandler`): `on_event(ctx, notice, change)`(`new`·`updated`·`closed`). 기본 비서도 이 능력을 구현한 앱 하나다 | ⬜ |
| P5-E6 | **이벤트 게시 도우미**(`announce_event`): 원장 선언(규칙 해시·앱 지정 포함)과 공지 게시를 한 번에 한다. 기본 비서의 개최와 앱들이 함께 쓴다 | ⬜ |

## 5-B. 검증

| 번호 | 요구사항 | 상태 |
|---|---|---|
| P5-B1 | **변조 점검표**: 과거 항목의 내용·참여자 서명·기록자 서명 변경, 항목 끼워 넣기, 순서 바꾸기, 가운데 항목 삭제를 감사가 모두 찾는다 | ⬜ |
| P5-B2 | **끝 잘라내기**는 감사만으로는 못 찾는다(체인이 여전히 맞음). 참여자가 보관한 기록자 서명 영수증과 대조하면 찾는다(`Receipts.missing_from(chain)`) | ⬜ |
| P5-B3 | **권한 없는 열람 점검표**: recorder 전체 열람(허용 목록 밖, 서명 없음, 다른 경로 서명, 시각 폭 밖의 다시 보내기), 접근 기록 열람, 닫힌 broker 그룹 검색, 관전 결과 열람이 모두 거부되고, recorder 접근 기록에 남는다 | ⬜ |
| P5-B4 | **반복 안정성**: 실제 LLM 경연 모티브 흐름과 앱 없는 가위바위보 인수 흐름을 여러 번 돌려 **성공률**, 소요 시간, 실패 지점을 잰다 | ⬜ |
| P5-B5 | 실행 기록을 `dev/phase5/evidence/`에 보관한다 | ⬜ |

## 5-C. 인수 확인: 가위바위보 (앱 없이)

> 2026-10-30 바로잡음: 처음에는 가위바위보 진행을 테스트용 앱 코드로 짰다. 이는 취지에 어긋난다. 이 단계는 **앱 없이 순수 플랫폼 기능만으로** 이벤트가 끝까지 도는지 확인하는 단계다. 경기 방식은 공지의 자연어 규칙에만 있고, peer의 **기본 비서**가 그 글을 읽고 범용 도구로 진행한다.

| P5-C40 | **배정(`assign` 항목)**(실제 실행 10에서 발견: 공개값은 모두 맞았지만, 한 선수가 대진표와 다른 상대와 m2를 치르고 그 상대도 서명함): 이벤트 발행자는 주제(예: 경기 번호)마다 맡을 당사자를 원장에 배정한다(발행자만, 주제마다 한 번, 이벤트에 계약된 사람만). 정책 `assigned_kinds`에 든 종류의 공동 확인은 배정된 당사자 그대로일 때만 원장이 받는다. 정책 `attest_kinds`가 있으면 그 목록의 종류만 받는다(실행 10: 종류에 도구 이름 "propose_attest"를 넣음). 둘 다 정책에 쓸 때만 켜진다 | ⬜ |
| P5-C41 | **기본 비서의 배정**: 개최자 도구 `assign`(필명으로 씀, 코드가 공개키로 바꿈). 진행 현황에서 배정을 읽어 "지금 상태"에 전체 배정과 "내 배정"을 코드가 적는다 | ⬜ |
| P5-C14 | 테스트 코드에 가위바위보 규칙이 없다. 개최 peer에게 규칙 글과 한 줄 지시만 주고, 판정은 원장만 본다 | ⬜ |
